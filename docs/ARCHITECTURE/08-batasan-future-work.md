# 8. Batasan & Future Work

> Bagian dari [dokumentasi arsitektur](../ARCHITECTURE.md) · Spesifikasi: [SPECS.md](../SPECS.md) · Panduan operasional: [DETAILS.md](../../DETAILS.md)

- **Watcher reload Nginx host** (SPECS §8.3) — perubahan direktori config dideteksi `inotifywait` lalu `nginx -t` + reload. Dashboard juga dapat me-reload nginx host lewat Docker socket (`NginxReloader`) sebagai pelengkap/fallback — tombol "Reload Nginx" + auto-reload setelah set/hapus custom domain, deploy/rebuild, dan SSL (best-effort, non-fatal).
- **Self-update** (§5.14) baru sebatas tombol manual: belum ada penjadwalan (cron/timer yang benar-benar menjalankan update), notifikasi hasil, changelog terstruktur (hanya tautan compare remote); migrasi skema SQLite antar-rilis **sudah** berjalan otomatis (`SchemaMigrations::LATEST = 4` — v1 skema awal, v2 registry server, v3 `parked_domains`, v4 `error_groups`/`error_events`, §5.19), tetapi rilis berikutnya yang mengubah skema tetap **wajib** menambah entri migrasi baru di `SchemaMigrations` — jangan mengandalkan `CREATE TABLE IF NOT EXISTS` untuk menambah kolom (GOTCHA §8 no. 1). Bila dashboard tetap tidak sehat setelah rollback otomatis, pemulihan manual lewat SSH tetap perlu.
- **SSL otomatis** (SPECS §8a/§8j.6a) sudah diimplementasikan: halaman `/domains` (tab **Semua Domain**; `GET /ssl` alias 302) + worker `cli/ssl.php` (app) & `cli/parked-ssl.php` (domain parkir) menjalankan certbot di container (HTTP-01 webroot / DNS-01 Cloudflare). Otomasi renewal `certbot renew` di host tetap prasyarat manual.
- **Subdomain app** (§5.6b): perubahan subdomain **tidak** menerbitkan ulang sertifikat otomatis — status SSL subdomain di-reset dan user menerbitkan ulang lewat tab Semua Domain (sertifikat terikat nama domain lama; berkas cert sengaja tidak dihapus; subdomain redirect akan mendapat 443 setelah cert subdomain aktif). Belum ada migrasi massal subdomain per-app maupun validasi panjang **FQDN total** (hanya label ≤ 63; `APP_DOMAIN` di luar kendali dashboard).
- **Deteksi konflik port** hanya terhadap app terkelola sendiri (SPECS §7.2), bukan container eksternal di host.
- **Multi-server — F0 + F1 + F2 + F3a + F3b/F3c + F3d + F4 (termasuk F4 lanjutan) + F4b mendarat & terverifikasi** (suite + probe assurance; rincian §5.21–§5.35): ekstraksi `DeployerInterface` → agent HTTP, mode runtime agent, registry server + scope per server, job async, TLS pinning, materialisasi artefak (§5.21–§5.26), **preflight ketersediaan nama app sebelum record dibuat** (`POST /apps/check`, read-only; `available:false` ⇒ pesan ramah di wizard, agent lama 404 ⇒ dilewati, respons tak terbaca ⇒ fail-closed, penegakan tetap di jalur job; §5.22 + GOTCHA no. 36), **Nginx/domain/SSL di server target** (§5.27), **log container + terminal SSE diproksi** (§5.28), **file manager per server** (§5.29), **monitoring per server** (`data.servers[]` + kartu UI `/monitor`, daftar server disaring **di server**, §5.30), **F3d: DB/Adminer, network & volume project per server** (§5.31), **F4 data: backup/restore/dump per server** (op job `backup_run|restore|db_dump`, `BackupDispatcher`/`BackupJobRunner`, registry ter-scope `server_id`) + **UI F4** (§5.32), **F4 lanjutan: op tingkat server `template_pull|self_update|restore_archived`, `AgentVersionGate` + `POST /servers/{id}/agent-update`, jadwal fan-out satu-clock, unduh `.sql` bertahap + retensi staging, `Run` one-shot di agent, halaman `/volumes` & `/apps` sadar-server** (§5.33–§5.35), dan **F4b: metering & tagihan per server** (akrual menuntut bukti container hidup di server app; kebijakan server offline tanpa akrual ganda — §5.18 (ii), SPECS §7.12). Yang **belum**:
  - **F3 sisa**: gateway Docker generik `/docker/*` belum ada (operasi per-resource sudah lewat route khusus). Sisa operasional lain dari F3d **selesai**: DB/Adminer diproksi, daftar volume project di agent, networks per server, view `/monitor` merender `servers[]`, `DatabaseController`/`NetworkController` **punya** penjaga server (§5.31), **`Run` (one-shot) app agent sudah diproksi** (agent `POST /terminal/run` → `DockerExec::runCommand()` yang sama, §5.34 — GOTCHA no. 13), `/apps` **sudah** merender kolom server + filter `?server=`, dan `/volumes` **sudah** sadar-server (§5.35).
  - **F4 sisa (terbuka)**: (1) **penghapusan/purge volume server agent** — `purge_orphans` tetap lokal-only & penghapusan volume agent belum punya op/job di agent (laporan eksplisit ke admin **ada**, penghapusan tidak; baris agent `can_purge=false`); (2) baris volume agent menampilkan `—` untuk driver/mountpoint/dibuat/ukuran (kontrak `GET /backups/volumes` tidak menginspeksi per baris); (3) **risiko higienitas sisa** — pesan galat worker (`cli/deploy.php`), `log_tail` job template pull, dan log billing `AppStopper` bisa memuat `AgentError` mentah. **Sudah selesai (bukan sisa)**: volume **yatim server agent kini terlihat** di `/volumes` (`VolumeController::collectAgentVolumes()` → `AgentDeployer::backupVolumes()` per server; admin selalu menghubungi setiap agent), unduh `.sql` mengirim `server_id` (`public/js/backup.js` → `dumpSqlItem()`/`volumeServerId()`), `Run` memilih server dari **data app** (`AgentDeployer::forApp()` — UI tidak perlu mengirim `server_id`), dan **redaksi identitas server seragam** di pesan yang tampil ke user (GOTCHA no. 25). **Sudah mendarat (F4 lanjutan)**: jadwal fan-out per server (satu clock di control plane) + exit code per volume/server, unduh `.sql` bertahap + retensi staging, restore arsip volume agent, template pull per server, self-update agen + `AgentVersionGate`/`POST /servers/{id}/agent-update` (§5.33–§5.34). **Sudah mendarat lebih dulu**: **metering & tagihan per server (F4b)** — akrual menuntut bukti container hidup di server app, kebijakan server offline tanpa akrual ganda (§5.18 (ii), SPECS §7.12).
  - **Terperbaiki (F3b)**: jalur UI control-plane **subdomain/rute/domain** kini sadar server (`AppNginxReloader`/`AppSslRevoker` → `AgentDeployer::reloadNginx()`/`revokeSsl()`); tidak ada lagi `NginxReloader`/`SslIssuer` **lokal** untuk app agent (GOTCHA §8 no. 15, §5.27, `tests/AppControllerAgentHostIsolationTest.php`). **Sudah selesai** juga: `saveCompose` app agent (`compose_content`) & override port app agent (`artifacts.files`).
  - **Penjaga antar-fase**: op yang belum didukung di server agent **ditolak eksplisit** (pesan fase F2/F3 atau `AgentError('unsupported')`), bukan dijalankan lokal — dilepas per fitur begitu fase-nya terverifikasi.
- Role & permission antar user — Phase 1 memakai 4 tingkat role tetap (admin/owner/operator/viewer, §5.10); permission granular per-resource belum ada.
- Log viewer per container sudah ada (modal di detail app, §5.11) — masih **polling** (3 detik); streaming SSE seperti terminal belum ada.
- Monitoring resource sudah ada di halaman global `/monitor` (§5.13) — kartu host dipoll tiap `MONITOR_POLL_MS` (default 7 detik) **hanya selama halaman terbuka**, sedangkan container masih **snapshot** (dipicu tombol Refresh); belum ada historis/grafik/alerting, angka volume hanya volume Docker (image & build cache belum; storage filesystem host ditampilkan terpisah sebagai kartu *Storage server* dan hanya untuk satu path `DISK_PATH`), I/O network/block belum ditampilkan, dan detail app **tidak** memuat panel monitoring (endpoint per app bisa ditambahkan dengan `ResourceCollector::collect([$app], false)` bila nanti diperlukan).
- **Batas resource** (§5.12a) sebatas **hard limit** per service (tanpa `reservations`) — bukan jaminan/kuota host: total limit bisa melebihi kapasitas host. Belum ada `!reset` untuk **menghapus** limit yang ditulis base compose repo (mengosongkan field hanya mengembalikan ke nilai repo), dan kompatibilitas keluarga field baru terverifikasi pada Compose v5.5.1 non-swarm. Sisa risiko: `compose_files` bisa menunjuk override limits yang sudah dihapus bila `AppStore::update()` gagal tepat setelah penghapusan (pola sama dengan override env/nama) — **dimitigasi defensif** oleh `ComposeSource::filterMissingGenerated()` di `LocalDeployer::resolveComposeFiles()` (§5.12a GOTCHA), sehingga entri yatim tidak pernah diteruskan ke `docker compose -f`. **App server agent**: limit diterapkan op job `apply_limits` dari **metadata** control plane; agent lama tanpa endpoint `GET /apps/{id}/services`/capability `apply_limits` tidak bisa mengatur limit (simpan ditolak dengan pesan perbarui agent), dan tab Sumber Daya memakai fallback service metadata — bukan kegagalan halaman (§5.12a).
- **Penyimpanan data domain** sudah pindah JSON → SQLite (§5.19); cache runtime (check/catalog/status/runs/state) **tetap** berformat JSON. Batasan yang tersisa: snapshot backup DB ditulis ke `db_backup_dir` (default di dalam volume `rames` yang sama) — **belum** ada salinan off-site/`restic` untuk DB dashboard (yang ada hanya backup **volume app** ke S3, §5.15); restore **wajib** diikuti `php start.php reload`; impor `database/*.json` hanya **sekali** (bukan sinkronisasi dua arah).
- **Template**: galeri hanya untuk create app baru — belum ada *upgrade* app yang sudah ada ke versi template terbaru, belum ada katalog dari sumber eksternal (registry/marketplace) atau template berbasis repo Git (template saat ini khusus compose prebuilt, §5.1c), dan template tidak bisa dikelola dari UI (masih file di repo, §4.5).
- **File manager container** (§5.16) sebatas operasi berkas pada container **hidup**: operasi berjalan **sebagai root** (`-u 0`) sehingga berkas/bind mount root host terjangkau, tetapi UI **belum** menyediakan kontrol permission/owner eksplisit (`chmod`/`chown`) maupun editor binary/hex, kompresi, atau pencarian isi berkas; pemulihan kepemilikan hanya best-effort untuk entri **baru** hasil `exec` (bukan unggahan `docker cp`), dan `mv` lintas device sengaja tanpa `chown`. Format arsip terbatas `.zip`/`.tar.gz`/`.tgz`; daftar direktori dipotong di `MAX_LIST_ENTRIES` = 5000 entri (ditandai `truncated`); editor teks dibatasi 2 MiB & menolak berkas biner (415). Deteksi biner bersifat heuristik (NUL / non-UTF-8 / rasio karakter kontrol) — berkas teks dengan encoding non-UTF-8 ditolak.
- Rootless Podman sebagai pengganti `docker.sock` untuk isolasi lebih baik.
- **Snippet Nginx mentah per app (Lapis B) belum ada** — §5.6a sengaja hanya mendukung rute **terstruktur** (path + target) agar dashboard bisa memvalidasi & membatasi sebelum menulis config; `include`/`server`/`listen`/`server_name` dari user tidak diizinkan (config invalid memblokir reload nginx seluruh host). Guard rollback juga belum mencakup `setDomain`/`removeDomain`/`cli/ssl.php` (SPECS §8.2a G3), belum ada lock per-app untuk penyimpanan rute yang bersamaan (SPECS §8.2a G5 — hanya `JsonStore::update()` yang terkunci, urutan snapshot→persist→reload→rollback tetap bisa *lost update*), dan penyimpanan belum **atomik terhadap crash** (SPECS §8.2a G8): proses yang mati antara persist `apps.json` dan reload/rollback bisa meninggalkan rute tersimpan sementara config di disk belum konsisten — penangkal sementara = jalankan ulang Simpan & Terapkan / Deploy Ulang.
- **Kredit & penagihan** (§5.18) sebatas meteran **tick inkremental** — dashboard mati ⇒ tick hilang ⇒ **under-count** (bukan over-charge); belum ada refund/void top-up, rate limiting top-up (diganti cap `BILLING_TOPUP_MAX_PENDING`), atau rekonsiliasi tagihan berbasis riwayat Docker (`StartedAt`). IP allowlist callback Duitku **tidak** ditegakkan di PHP (dashboard di balik Nginx host ⇒ `REMOTE_ADDR` bukan IP asli) — ditawarkan opsional di level Nginx host, pertahanan utama tetap HMAC. `adjust` negatif tidak langsung memicu auto-stop (baru saat `Invoicer`/tick menutup periode yang punya pemakaian tertunggak, bila saldo `< 0`; halaman `/credits` kini menampilkan hint ini). Penagihan periode digerbang tanggal `BILLING_INVOICE_DAY` (dijepit 1–28) dengan catch-up. **N2 (tertutup sejak worker berparitas penuh)**: dulu app tanpa owner/owner tak dikenal → controller menolak aktor member sementara worker (hanya menilai owner) meloloskan; kini `cli/deploy.php` menerima id aktor (`argv[4]`) dan menilai **aktor → pembayar/owner** (urutan exempt sama) sehingga putusan controller & worker konsisten — hanya pemanggil lama tanpa `argv[4]` yang tetap menilai owner saja. **Anti-escape pengalihan kepemilikan**: app berjalan yang dialihkan ke pemilik bebas tagihan (manual `transferOwner` **atau** hapus user) dihentikan otomatis (`REASON_TRANSFER`). **N7 (defensif)**: `billingPayerFor()` jatuh ke aktor bila `auth.json` tak terbaca (`AuthMiddleware` tetap penjaga utama). **I2 (pengecualian disengaja)**: `AppStore::assignMissingOwners()` (dipakai `AuthController`/`command/AssignOwner`/`command/MakeAdmin`) **tidak** memicu stop — hanya menyentuh app ber-`owner_id` kosong yang memang **tidak pernah diakru** (`UsageMeter` melewatinya), sehingga tidak menghapus akrual berjalan & tidak menciptakan escape.

- **Rekam Error** (§5.43, SPECS §7.18) sudah berjalan di control plane, dengan batasan fase 1: error di **server agent belum dikirim** ke control plane; **halaman login belum melapor**; belum ada tombol "Laporkan masalah" manual, notifikasi email/webhook, maupun uji HTTP hidup/JS di browser pada CI; `BillingServerRateWiringTest` (pra-eksisting, non-fitur) masih menyentuh DB runtime dan butuh isolasi terpisah. Migrasi v4 dibuktikan pada DB temp; bila berkas DB runtime dimiliki root (0600/640), jangan mengandalkan uji yang menulis ke sana.

#### GOTCHA multi-server (F0–F4)

Dua puluh satu jebakan dari F0–F4 + enam dari F4 lanjutan (op tingkat server, versi agen, restore arsip, jadwal fan-out, halaman sadar-server) + satu dari penerbitan SSL HTTP-01 (webroot tidak terbaca nginx host, preflight & hint 403) + dua dari installer server agent (`--bind` tanpa `:`, berkas env ber-CRLF & header installer lama) + dua dari mode AJAX SSL & filter daftar app + satu dari urutan skrip vs markup modal di halaman Config + dua dari siklus hidup app di server agent (nama app tetap terpakai setelah app dihapus; direktori artefak sisa memblokir create dengan nama sama) + satu dari preflight ketersediaan direktori app sebelum create (saran, bukan penegak; agent lama dilewati 404) + satu dari kepemilikan `.git` pada self-update (galat `insufficient permission … unpack-objects failed` dan `detected dubious ownership`, yang dulu dilaporkan UI sebagai masalah jaringan/DNS) + satu dari template yang meng-override `entrypoint` demi `apk add` + turun hak (`su-exec`) pada bind mount project host (kepemilikan berkas campuran, `OPENCODE_PROJECTS_DIR` wajib, `create_host_path: false`) + satu dari worker deploy **detached yang kehilangan seluruh environment** (`pcntl_exec` `envp` kosong = lingkungan kosong, bukan pewarisan; app mandek `status=deploying, stage=queued`) + **dua belas dari domain parking & halaman `/domains`** (rollback wajib, `PARKED_ROOT`, izin baca nginx host, backup konten, server lokal-only, prefiks `_parked_`, `www`, fallback cert hilang, cert subdomain redirect, config gagal pasca-issue, `/ssl` hanya alias, baris non-admin) — **total 51 entri** — yang **terbukti** saat implementasi; format gejala → sebab → penangkal.

> **1. GOTCHA — `CREATE INDEX` sebelum `ALTER TABLE` pada tabel lama.** **Gejala**: migrasi v2 gagal `no such column: server_id`. **Sebab**: `SchemaMigrations::ensure()` menulis `CREATE TABLE IF NOT EXISTS` lalu `CREATE INDEX`; pada tabel `apps_apps` yang sudah ada, `CREATE TABLE IF NOT EXISTS` tidak menambah kolom baru, sehingga `CREATE INDEX ("server_id")` menabrak kolom yang belum ada. **Penangkal**: `SchemaMigrations::ensureDerivedColumns()` — tambah kolom yang hilang lewat `ALTER TABLE` (deteksi `PRAGMA table_info`) **dulu**, indeks **kemudian**.

> **2. GOTCHA — middleware bersifat GLOBAL.** **Gejala**: `/healthz` agent dilewatkan CSRF/Auth sesi sehingga gagal (419/302) walau digerbangi di `route.php`. **Sebab**: daftar middleware global (`'' => [CsrfMiddleware, AuthMiddleware, StaticFile]`) berlaku untuk semua route; gerbang mode hanya di `config/route.php` tidak cukup. **Penangkal**: mode agent **wajib** digerbangi di `config/middleware.php` juga (mode `dashboard` ⇒ CSRF→Auth→StaticFile, mode `agent` ⇒ `AgentAuthMiddleware` saja).

> **3. GOTCHA — CSRF hanya membaca `_token` dari body.** **Gejala**: request AJAX baru (tombol Test connection) ditolak **419** walau sudah mengirim `X-CSRF-TOKEN`. **Sebab**: `CsrfMiddleware` hanya membaca `$request->post('_token')`. **Penangkal**: kirim `_token` di **body** (form-urlencoded) — pola yang sama dengan `public/js/update.js`/`template-pull.js`/`backup.js`; jangan melebarkan jalur header.

> **4. GOTCHA — `server_id` dipetakan ke `local` saat proyeksi di agent.** **Gejala**: seluruh deploy di agent gagal karena `DeployerFactory::createForApp()` melempar "Server tidak dikenal". **Sebab**: payload job membawa id server **control plane**, sedangkan store agent hanya mengenal `local`. **Penangkal**: `AgentAppProjection::upsert()` **wajib** memetakan `server_id` payload ke `ServerStore::LOCAL_ID` sebelum menulis ke `AppStore` agent.

> **5. GOTCHA — log deploy dipakai bersama antar-job.** **Gejala**: halaman detail app mengulang baris log job lama saat polling job kedua. **Sebab**: log deploy adalah berkas **per-app** (`runtime/logs/deploy/{appId}.log`) — bukan per-job — jadi `offset=0` mengirim ulang isi lama. **Penangkal**: control plane **wajib** mulai dari `log_offset` yang dikembalikan `POST /jobs` (atau header `X-Rames-Offset`), bukan 0.

> **6. GOTCHA — memo per-proses `ServerResolver`.** **Gejala**: daftar app jadi O(n) query registry server (satu query per baris) saat `app_subdomain_of()` dipanggil per baris. **Sebab**: resolver membaca store tiap panggilan. **Penangkal**: `ServerResolver::$memo` meng-cache snapshot dengan kunci **cap berkas DB (path + mtime + size, termasuk `-wal`/`-shm` — SQLite baru menyentuh berkas utama saat checkpoint)** + `forgetMemo()`. Ini pengecualian sadar larangan cache lintas-request: selalu divalidasi ulang terhadap cap berkas.

> **7. GOTCHA — baris `local` mengunci field identitas.** **Gejala**: menyimpan `name`/`kind`/token server lokal dari form ditolak (atau, bila tidak dikunci, membuat "server ini sendiri" tak lagi cocok dengan `.env`). **Sebab**: identitas server lokal berasal dari `.env`/`config('deploy.*')`. **Penangkal**: hanya `domain`, `notes`, & `rates` yang boleh diubah; aturannya **hanya** di `ServerResolver::validateLocal()` (controller tidak boleh menyalin). `port_range` lokal dikunci karena sumber kebenarannya `.env` (`PORT_RANGE_START`/`PORT_RANGE_END`).

> **8. GOTCHA — `port_range[start]/[end]` kosong bukan "kosong".** **Gejala**: form server gagal/melempar saat kedua field rentang port dibiarkan kosong. **Sebab**: `ServerResolver::normalizePortRange()` melempar untuk bentuk setengah terisi. **Penangkal**: form memakai field `port_range_start`/`port_range_end` dengan arti **pasangan kosong = tidak diset** (bukan rentang kosong); pasangan setengah terisi tetap ditolak.

> **9. GOTCHA — `GET /healthz` & `/version` agent juga butuh token.** **Gejala**: `curl https://<agent>:8443/healthz` tanpa header token balas **401** (bukan 200) — "Test connection" gagal. **Sebab**: keputusan keamanan menutup **seluruh** permukaan agent. **Penangkal**: selalu sertakan header token (`Authorization`) saat memanggil agent (installer melakukannya untuk verifikasi lokal); jangan menambah route publik di agent.

> **10. GOTCHA — sertifikat agent 825 hari tanpa rotasi otomatis.** **Gejala**: suatu hari Test connection gagal (`tls_failed`) padahal konfigurasi tidak berubah — sertifikat agent sudah kedaluwarsa/diganti. **Sebab**: tidak ada rotasi otomatis; `install.sh --force` mengganti cert + token. **Penangkal**: perbarui server di halaman **Servers** setelah `--force`; dashboard otomatis mereset state koneksi bila `base_url`/token/PEM berubah. Jangan pernah mematikan verifikasi TLS sebagai "solusi" — itu menghapus pinning.

> **11. GOTCHA — helper reload Nginx bersifat privileged (`docker run --privileged -v /:/host`).** **Gejala**: menjalankan test yang menyentuh jalur reload Nginx membuat `docker run` sungguhan terhadap root host (bisa me-reload Nginx host test-runner) atau menggantung menunggu image. **Sebab**: `NginxReloader::reload()` menjalankan helper container `--network host --pid host --privileged -v /:/host` yang `chroot` ke root host untuk `nginx -t` + `nginx -s reload` (§8.3/§8.4) — bukan operasi murni in-process. **Penangkal**: test apa pun yang menempuh jalur itu **wajib** membuat `NGINX_RELOAD_IMAGE`/`NGINX_BIN` (config `deploy.nginx_reload_image`/`deploy.nginx_bin`) **tidak tersedia** dan menyuntikkan reloader palsu (`NginxConfigGuard` menerima `NginxReloader` yang bisa di-subclass); jangan pernah memanggil reload nyata dari suite.

> **12. GOTCHA — stream SSE proxy memakai Guzzle StreamHandler, bukan cURL.** **Gejala**: jalur streaming terminal ke agent **tidak** bisa dibaca bertahap bila memakai handler cURL (`CurlHandler` membaca seluruh body lebih dulu → bukan byte-passthrough). **Sebab**: `AgentDeployer::terminalStream()` membaca respons agent secara inkremental, yang hanya didukung `GuzzleHttp\Handler\StreamHandler`. **Penangkal**: proksi streaming WAJIB lewat `StreamHandler` (bukan cURL), dan **jalur streaming belum di-smoke terhadap agent nyata** — smoke end-to-end menunggu uji di server agent sungguhan; jangan menjanjikan streaming real-time tanpa uji itu.

> **13. GOTCHA — `Run` (one-shot) app server agent WAJIB diproksi ke agent (dahulu sengaja 501).** **Gejala** (historis): tombol **Run** pada app server agent balas `501`; **kini** `TerminalController::run()` meneruskan ke `AgentDeployer::runCommand()` → agent `POST /terminal/run` (`DockerExec::runCommand()` di server itu) sehingga hasilnya setara jalur lokal. **Sebab aturan lama**: mengeksekusi Run di control plane akan menjalankannya di **host yang salah** (container app tidak ada di sana, atau lebih buruk: container bernama sama milik app lain). **Penangkal**: `run()` **wajib** memilih `agentDeployer($app)` lebih dulu dan menolak bila agent tidak dapat dipakai — **jangan pernah** "fallback" menjalankan perintah di Engine host control plane untuk app agent (aturan isolasi host yang sama dengan seluruh F1–F4).

> **14. > **28. GOTCHA — HTTP-01 gagal `403` ⇒ berkas challenge ADA tetapi nginx host menolak menyajikannya (webroot tidak terbaca).** **Gejala**: `ssl_issue` (di server agent: job `ssl_issue` dari `AgentDeployer::issueSsl()`, §5.27) gagal dengan `Detail: … 403` — padahal blok acme **sudah** dirender (`location ^~ /.well-known/acme-challenge/ { root <webroot>; }`, `NginxConfigGenerator::render()`, `app/library/Nginx/NginxConfigGenerator.php:50-54`) dan certbot **berhasil menulis** berkas challenge ke `SSL_WEBROOT`. Pembeda cepat di blok `Detail:` (yang terbaca berkat GOTCHA no. 26): **`404`** = path/`root` salah atau berkas belum ditulis; **`403`** = ditolak **membaca/menyajikan** (izin/path/aturan); **`Timeout`** = port 80/DNS tidak sampai. **Sebab**: worker nginx host berjalan sebagai user tak-privilege (`www-data` di Debian/Ubuntu, `nginx` di RHEL — master tetap root), **bukan** root, jadi salah satu dari — (a) salah satu komponen path webroot **tidak *traversable*** oleh user nginx (pola khas: repo/instalasi di bawah `/root` yang `0700`); (b) izin direktori/berkas challenge sendiri (mis. `0700`) sehingga nginx tak bisa masuk/membaca; (c) **aturan global yang menang** atas blok `location ^~` — mis. `deny all` untuk dotfile: `^~` memenangkan **pencocokan** regex, **bukan** direktif `deny`, jadi permintaan tetap ditolak; (d) ada **vhost lain/sisa** yang cocok untuk domain itu dan mengembalikan 403. **Penangkal**: diagnosa — `tail /var/log/nginx/error.log` (cari `Permission denied` / `directory index of`), `namei -l <SSL_WEBROOT>/.well-known/acme-challenge` (semua komponen path harus punya bit `x` untuk user nginx), `sudo -u www-data test -rx <SSL_WEBROOT>/.well-known/acme-challenge && echo ok`, lalu **tiru Let's Encrypt**: tulis berkas probe di direktori itu + `curl -sS -D- http://<domain>/.well-known/acme-challenge/<probe>` **dari luar** host (bukan dari localhost) dan pastikan balasan `200`, bukan 403. Perbaikan: **pindahkan instalasi ke path yang *traversable*** (mis. `/srv/...`, bukan `/root/...`) **ATAU** set `SSL_WEBROOT` (env `SSL_WEBROOT` → `config/deploy.php:141` `deploy.ssl_webroot`) ke direktori yang **traversable & terbaca user nginx host** — dengan syarat mutlak: direktori itu **juga harus terlihat di dalam container** (yang menulis berkas challenge adalah certbot **di container**), dan compose agent hanya mem-bind **`${PWD}:${PWD}`** (`docker-compose.agent.yml`) serta `/etc/letsencrypt`, jadi jalur yang aman adalah **di dalam path repo** (mis. `{proyek}/webroot` bawaan atau subdirektori repo, `0755`); memindahkannya ke luar repo (mis. `/var/www/...`) menuntut **bind mount tambahan** di compose (pemilik: Deploy & Docker). Lalu **tulis ulang vhost** (Deploy Ulang / job `nginx_write`) supaya `root` blok acme menunjuk direktori baru — di server agent `SslIssuer`/`NginxConfigGenerator` membaca `deploy.ssl_webroot` **server itu**. Baris `SSL_WEBROOT=…` ditulis di **wilayah operator** `secrets/agent.env` (di bawah sentinel `# rames-installer:preserved`) sehingga **tidak terhapus** oleh rerun `agent/install.sh` (lihat §4.5 & `agent/README.md` §"Rahasia & sumber konfigurasi"); env baru hanya terbaca setelah container di-**recreate** (bukan `restart`; `up -d` sudah cukup — isi `env_file` dihitung Compose, lihat `agent/README.md` "Prasyarat SSL"). Terkait: SPECS §8.2a G2 (**DILARANG** menghapus/menimpa blok `location ^~ /.well-known/acme-challenge/`) — jangan "memperbaiki" 403 dengan menambah `deny`/mengubah blok acme di jalur rute. **Preflight `SslIssuer::assertChallengePathServable()` (terbukti, menghemat rate limit).** `issue()` memanggil preflight **setelah `prepareDirs()` dan sebelum certbot**, sehingga kelas kegagalan `403` dipastikan lebih dulu dan jatah rate limit Let's Encrypt tidak terbuang untuk vhost yang sudah pasti tak bisa dilayani. Menyembunyikan tab/tombol di view bukan pengaman. **Penangkal**: pertahankan filter di `DomainController::table()` + `decorateRows()` dan cek `guard()`/admin **sebelum** I/O pada seluruh aksi pengelolaan; jangan menambahkan endpoint baru yang mengembalikan `ParkedDomainStore::all()` tanpa cek admin.

> **52. GOTCHA — instruksi firewall onboarding agent WAJIB menyebut port web publik 80 & 443, bukan hanya port agent.** **Gejala**: di server agent yang baru dipasang, tombol SSL gagal dengan `Detail: <domain>: Timeout during connect (likely firewall problem)` sementara DNS benar, `ADMIN_EMAIL` terisi, `SSL_WEBROOT` lolos preflight, dan container agent sehat — port `8443` terbuka (dari jaringan mana pun) tetapi `80`/`443` *timeout* dari seluruh internet (ICMP & `8443` menjawab, `80`/`443` dibuang). **Sebab**: blok onboarding `agent/install.sh` (`print_onboarding()`) hanya memberi perintah `ufw allow … port 8443`, sehingga operator yang mengikuti instruksi persis meninggalkan `80`/`443` tertutup — padahal Nginx host melayani app di sana dan certbot memvalidasi HTTP-01 dari **IP acak Let's Encrypt** (allowlist IP di port 80 mustahil lolos). Gejalanya menyesatkan karena tidak ada yang salah di Rames: `Timeout during connect` adalah kegagalan TCP di depan Nginx, bukan `404`/`403` (webroot, GOTCHA no. 28) maupun `DNS problem`. **Penangkal**: pertahankan **dua** kelompok port di onboarding & `agent/README.md` — (1) port agent hanya untuk IP control plane (keamanan), (2) `80`/`443` terbuka untuk **semua** (fungsi). Verifikasi dari mesin luar: `curl -sS -m 8 -o /dev/null -w '%{http_code}\n' http://<domain>/` harus mengeluarkan kode HTTP, bukan timeout; bila port 80 tak boleh publik gunakan DNS-01 (`SSL_CHALLENGE=dns-cloudflare`), tetapi `443` tetap wajib.

> **53. GOTCHA — menghapus server lebih dulu membuat app-nya "yatim" dan dulu TIDAK BISA DIHAPUS sama sekali.** **Gejala**: setelah baris server dihapus di halaman Servers, tombol Hapus pada app yang pernah dideploy di sana selalu gagal dengan "Gagal menghapus: Server tidak dikenal: "<id>". …" — app tidak pernah hilang dari daftar walau sudah di-Retry berkali-kali; halaman **detail** app itu pun tidak bisa dibuka (500 `RuntimeException` "Server tidak dikenal"), sehingga tab Hapus App tak pernah terjangkau; operasi lain (deploy/stop/log/SSL) juga menolak dengan pesan yang sama. **Sebab**: `AppController::delete()` memakai `DeployerFactory::createForApp()` → `ServerResolver::resolveForApp()` yang **fail-fast** untuk `server_id` tak dikenal (aturan inti multi-server: jangan pernah fallback ke server lokal), sehingga jalur pembersihan record ikut terblokir selamanya — padahal server itu memang sudah tidak ada, jadi teardown remote mustahil. `detail()` melakukan hal yang sama **tanpa** penjaga, jadi halaman detail (satu-satunya tempat tombol hapus) ikut 500. Faktor pemburuk: teks konfirmasi hapus server sudah menjanjikan "app … berhenti dikelola dashboard" (bukan ikut terhapus), tetapi janji itu tidak punya jalur implementasi. **Penangkal**: (1) `detail()` membungkus pembuatan deployer (`$deployer = null` bila server tak dikenal) sehingga halaman tetap terbuka dan tab Hapus App terjangkau — daftar kontainer/volume tampil kosong; (2) `ServerResolver::findForApp()` (varian **`null`** khusus jalur hapus) membedakan "baris server benar-benar hilang" (`null`) dari "registry tidak terbaca" (tetap **melempar** — kegagalan I/O tidak boleh disimpulkan sebagai "server dihapus"). `delete()` lalu: server ditemukan ⇒ teardown seperti biasa; `null` ⇒ teardown **dilewati** (DILARANG dialihkan ke server lokal), record app + artefak lokal (direktori, deploy key, managed env) tetap dibersihkan, dan flash `info` menyebut bahwa container/volume di server itu **tidak** di-teardown sehingga harus dibersihkan manual (`docker compose -p <project> down -v`). **WAJIB**: varian toleran ini **hanya** untuk pembuangan record; seluruh operasi lain tetap memakai `resolveForApp()`. Bukti: `tests/AppControllerServerScopeTest.php` (`testDeleteOfAppOnRemovedServerSkipsTeardownAndKeepsTheRecordRemovable`, `testDetailOfAppOnRemovedServerStillRendersSoItCanBeDeleted`), `tests/ServerResolverTest.php` (`testFindForAppReturnsNullOnlyWhenTheServerRowIsGone`, `testFindForAppStillThrowsWhenTheRegistryIsUnreadable`).

> **54. DILARANG — menormalkan allowlist invalid menjadi `[]` (yang berarti "semua server").** **Gejala**: admin mencabut/merapikan akses server seorang member (mis. seluruh id yang dicentang ternyata sudah dihapus dari registry), lalu member itu justru bisa memilih **semua** server — eskalasi hak tanpa niat. **Sebab**: `server_ids` kosong didefinisikan sebagai "semua server"; membuang semua id tak dikenal lalu menyimpan `[]` mengubah "tidak ada yang valid" menjadi "semua". **Penangkal**: `POST /users/{id}/servers` **menolak** perubahan (flash error, store tidak berubah) bila `server_ids` dikirim tidak kosong tetapi tidak ada satu pun id dikenal (fail-closed; registry tak terbaca juga menolak). Id asing yang tercampur id valid dibuang, id valid disimpan. Bukti: `tests/UserStoreServerAccessTest.php`, `tests/ServerAccessTest.php`.

> **55. DILARANG — mengirim metrik `host` server yang hanya terlihat karena grant, tanpa app user di sana; WAJIB tetap menyaring baris lewat `AppAccess`/`BackupAccess`.** **Gejala**: member pemegang grant `server_select` menerima CPU/RAM/disk host server tempat ia belum punya app (kebocoran kapasitas infrastruktur), atau melihat baris app/backup user lain karena "servernya kelihatan". **Sebab**: `ServerAccess::visibleServers()` adalah **union** (app terlihat ∪ server grant) — memakainya langsung untuk `/api/monitor/overview`/daftar baris melebar dari "server boleh dipilih" menjadi "data boleh dibaca". **Penangkal**: `overview` hanya merakit entri server yang menaungi minimal satu app `AppAccess::visible()`; daftar app/backup tetap disaring `AppAccess::visible()`/`BackupAccess::can()`; grant tidak menambah ability `AppAccess`. Bukti: `tests/ServerAccessTest.php`, `tests/FileMonitorServerProxyTest.php`, `tests/AppControllerServerGrantTest.php`.

#### GOTCHA tema tampilan (mode gelap, §5.42)

Lima jebakan dari fitur murni-klien ini — bukan bagian daftar multi-server di atas; format tetap gejala → sebab → penangkal.

> **T1. WAJIB — skrip boot tema berada di `<head>` SEBELUM stylesheet.** **Gejala**: halaman sempat tampil terang (atau gelap) satu frame lalu berubah — *flash of incorrect theme*, terutama pada dark mode. **Sebab**: atribut `data-bs-theme` disetel setelah CSS/komponen sudah dilukis. **Penangkal**: `app/view/partials/theme-boot.php` **wajib** di-include di `<head>` **sebelum** `<link rel="stylesheet">` pada ketiga halaman (`partials/header.php`, `auth/login.php`, `index/hello.php`); jangan memindahkannya ke footer atau menggabungkannya ke `theme.js` (skrip footer terlambat).

> **T2. DILARANG — memakai nilai `system` pada `data-bs-theme`.** **Gejala**: tema tidak berubah di mode `system`, atau komponen Bootstrap kembali ke default terang walau OS gelap. **Sebab**: Bootstrap 5.3 hanya mengenal `light|dark`; nilai lain diabaikan. **Penangkal**: `data-bs-theme` **selalu** nilai ter-resolve (`resolve(mode)`); `system` hanya boleh ada di `data-theme-mode` (pemilih ikon) dan di `localStorage`.

> **T3. GOTCHA — `bg-white`/`bg-light` Bootstrap mengunci warna terang di tema gelap.** **Gejala**: header kartu/panel tetap putih menyilaukan saat dark mode. **Sebab**: utilitas itu warna **literal**, bukan variabel tema. **Penangkal**: pakai `bg-body`/`bg-body-tertiary` (mengikuti `--bs-body-bg`/`--bs-tertiary-bg`); bila menemukan `bg-white`/`bg-light` baru di view, ganti — jangan menambal dengan override CSS per halaman.

> **T4. GOTCHA — kartu Bootstrap di dark memakai `--bs-card-bg = --bs-body-bg` sehingga menyatu dengan latar.** **Gejala**: batas kartu hilang di tema gelap (kartu tampak menyatu dengan halaman). **Sebab**: default Bootstrap dark menyetel `--bs-card-bg` sama dengan body. **Penangkal**: blok `[data-bs-theme="dark"]` di `public/css/app.css` **wajib** menyetel `--bs-card-bg: var(--bs-secondary-bg)`; jangan menghapus override ini saat merapikan token.

> **T5. CATATAN — media logo template sengaja tetap terang di kedua tema.** **Gejala**: `.template-tile-media` terlihat sebagai kotak terang di dark mode dan bisa dilaporkan sebagai "tema tidak konsisten". **Sebab**: logo SVG/PNG transparan umumnya berwarna gelap sehingga tak terbaca di atas latar gelap. **Penangkal**: pertahankan `--template-media-bg` (`#f8fafb` light, `#e7edf0` dark) dan **jangan** mengubahnya menjadi `--bs-body-bg`; ini pengecualian yang disengaja (SPECS §7.17), sama seperti teks non-kode log/terminal yang tetap gelap.
