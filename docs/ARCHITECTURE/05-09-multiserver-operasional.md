## 5.27 Nginx & SSL per Server (F2)

Semua operasi Nginx/SSL app server agent berjalan **di server itu** (agent memakai library Nginx/SSL-nya sendiri) — control plane **tidak** menyalin logika/path Nginx.

**A. Job async (op F2)** — route `POST /jobs` (`AgentJobController`), dieksekusi cabang mode `cli/deploy.php` **sebelum** gerbang kredit:

| Op | Yang dijalankan di agent (`cli/deploy.php`) |
|---|---|
| `nginx_write` | `DeployerFactory::createForApp($app)->writeNginxConfig($app)` → `LocalDeployer::renderNginxConfig()` (webroot/letsencrypt/domain **milik agent**) + `NginxReloader::reload()` |
| `nginx_remove` | `removeNginxConfig($app)` + reload |
| `nginx_reload` | `NginxReloader::reload()` saja (gagal ⇒ job `error`) |
| `ssl_issue` | `SslIssuer::issue($domain)` (certbot + `deploy.letsencrypt_path` server itu) → set slot `ssl`/`custom_ssl` `active` + `_expires_at` dari `certExpiry()` → tulis ulang vhost + reload. Preflight webroot (`assertChallengePathServable()`) & hint `403` berjalan **di server itu** sebelum/sesudah certbot (GOTCHA no. 28) |
| `ssl_revoke` | `SslIssuer::revoke($domain)` → slot `disabled` → tulis ulang vhost + reload |

- `domain` datang dari **payload job** (dibersihkan/dinormalisasi; satu-satunya field payload tambahan yang diizinkan — kredensial DNS **tidak pernah** melintas: agent memakai berkas kredensial yang sudah ada di server itu, mis. `CLOUDFLARE_CREDS`).
- **`ADMIN_EMAIL` wajib ada di server yang mengeksekusi `ssl_issue`.** Karena job dijalankan `cli/deploy.php` **di server agent**, identitas ACME dibaca dari env server itu (`SslIssuer::buildCommand()`, `app/library/SSL/SslIssuer.php:514-518` ⇒ melempar "ADMIN_EMAIL belum diatur …" bila `config('deploy.admin_email')` kosong; env → `config/deploy.php:136`). Di server agent nilainya tinggal di blok kelolaan `secrets/agent.env` (dibuat/diperbarui `agent/install.sh --email`; **bukan** `.env` dashboard), sedangkan penyetelan webroot (`SSL_WEBROOT`) ditulis di **wilayah operator** berkas yang sama dan tidak terhapus rerun (§4.5). Mengisi/mengubah env tetap **wajib recreate** container agent (env dibaca saat create).
- Slot SSL ditentukan `$sslSlotFor()`: `custom_ssl` bila `domain == custom_domain`, `ssl` bila `== app_subdomain_of($app)`, selain itu **galat** (domain bukan milik app).
- `AgentDeployer::writeNginxConfig()`/`removeNginxConfig()`/`reloadNginx()` melempar `AgentError('unsupported')` bila agent menolak; **tidak ada** fallback ke `LocalDeployer`.

**B. Endpoint non-job** (read-only / app-less, ≤30 s):

| Endpoint (agent) | Isi |
|---|---|
| `GET /apps/{id}/nginx` | Config vhost **hasil perakitan di agent** (`DeployerFactory::createForApp($app)->renderNginxConfig($app)`) → `{code:0, op:'nginx_render', config}`. App tak dikenal ⇒ 404; app tanpa vhost (tak mem-publish port host) ⇒ 409 |
| `POST /nginx/check` | preflight `DeployerFactory::create()->ensureWritable()` (bukan job: `ensureWritable()` tanpa app) → `{code:0, op:'nginx_check', ok:true}` / 500 |
| `POST /apps/check` | preflight **ketersediaan direktori app** `apps/<name>` (bukan Nginx, bukan job; ditempatkan di sini sebagai tetangga `POST /nginx/check`): `{app:{id,name,repo_url?}}` → `{code:0, op:'app_check', available, state, message}` via `AgentArtifactMaterializer::appDirState()` — read-only, satu pembacaan direktori. Payload tak sah ⇒ **400 `invalid_request`**, galat sisi agent ⇒ **500 `app_check_failed`** (pesan di sana hanya dipangkas `sanitizeMessage()`, **bukan** diredaksi — redaksi token/PEM/`base_url` terjadi di sisi master, §5.22). Dipakai `AgentDeployer::assertAppTargetAvailable()` dari `AppController::createAndDeploy()` (detail & semantik state: §5.22, §5.24) |

**C. Jalur SSL control plane** — `SslController::enable()` **sadar server**: untuk app agent ia `assertDomainBase()` (server tanpa `APP_DOMAIN` ditolak lebih awal) lalu spawn worker; worker `cli/ssl.php` memilih `DeployerFactory::createForApp()` → `AgentDeployer::issueSsl()` (job `ssl_issue`) dan **menarik** state SSL (`GET /apps/{id}`) untuk `_expires_at`. `AgentDeployer::revokeSsl()` = job `ssl_revoke`.

> **TERPERBAIKI (F3b, terverifikasi assurance).** Jalur UI `setSubdomain()`/`saveRoutes()`/`setDomain()`/`removeDomain()` kini **sadar server** lewat satu pintu per operasi (tidak ada `new NginxReloader()`/`new SslIssuer()` lokal di `AppController`):
> - subdomain & rute → `AppNginxReloader` (`NginxConfigGuard` menerimanya apa adanya): app lokal ⇒ `NginxReloader` lama, app agent ⇒ job `nginx_reload` (`AgentDeployer::reloadNginx()`) — termasuk **jalur rollback** guard, sehingga host control plane tidak pernah di-reload untuk app agent;
> - custom domain → `AppSslRevoker`: app lokal ⇒ `SslIssuer::revoke()`, app agent ⇒ job `ssl_revoke` (`AgentDeployer::revokeSsl()`) — `ssl_revoke` akhirnya terpakai dari UI.
>
> `server_id` tak dikenal / deployer bukan `AgentDeployer` ⇒ **melempar** (fail-fast, tanpa fallback lokal). Bukti: `tests/AppControllerAgentHostIsolationTest.php` (spy reloader/issuer lokal = 0 panggilan, op agent benar, rollback & fail-fast, app lokal tetap perilaku lama). Rincian: §8 GOTCHA no. 15.

**Pengujian**: `tests/AgentDeployerNginxTest.php`, `tests/SslControllerServerTest.php`, `tests/AppControllerServerScopeTest.php`, `tests/AgentJobControllerTest.php`, `tests/AppControllerAgentHostIsolationTest.php`.

## 5.28 Log Container & Terminal Diproxy (F3a)

Sesi terminal app agent **hidup di agent** (`DockerExec`, FIFO di `runtime/terminal/{token}/` server itu); control plane hanya **mem-proxy** apa adanya.

| Endpoint (agent) | Isi |
|---|---|
| `GET /apps/{id}/logs?container=&tail=&timestamps=` | Log container app dari Engine server itu (`DockerClient` agent) |
| `POST /terminal/open` | Buka sesi (`DockerExec::open()`), balas `token` |
| `GET /terminal/{token}/stream` | SSE chunked dari sesi |
| `POST /terminal/{token}/input` | Kirim input |
| `POST /terminal/{token}/close` | Tutup sesi |

- **Kontrak token**: `app_id` ikut di query/body tiap panggilan → validasi "token milik app ini" tetap satu sumber di `DockerExec::sessionInfo($token, $appId)`; token saja tidak cukup.
- **Control plane** (`LogController`, `TerminalController`) memilih deployer lewat `AgentDeployer::forApp($app)` (pintu tunggal resolusi `server_id`); `null` ⇒ jalur lokal lama. Untuk app agent: `AgentDeployer::containerLogs()` (`GET /apps/{id}/logs`) dan `AgentDeployer::terminalStream()` (`GET /terminal/{token}/stream`).
- **SSE byte-passthrough**: `TerminalController::proxyAgentStream()` mengembalikan `Webman\Http\Response` + `SSE_HEADERS` (chunked) dan mengalirkan chunk via `Timer` (`PROXY_TICK`) → `$connection->send(new Chunk($chunk))`; **tidak** di-buffer penuh di memori.
- **Sesi agent TIDAK ditutup saat klien drop** (aturan repo): `$connection->onClose = $cleanup` **hanya** menutup socket upstream (`$stream['close']()`), sesi tetap hidup di agent sampai `close`, proses keluar, atau prune TTL — sehingga `EventSource` boleh menyambung ulang. `AgentLogController`/`AgentTerminalController` **tidak** menulis audit (identitas pelaku hanya di control plane).
- **`Run` (one-shot) untuk app agent diproksi ke agent** (bukan dieksekusi lokal): `TerminalController::run()` memilih `agentDeployer($app)` lebih dulu dan memanggil `AgentDeployer::runCommand()` → agent `POST /terminal/run` (`DockerExec::runCommand()` di server itu, non-interaktif, timeout ≤600 dtk) — hasil setara jalur lokal (GOTCHA §8 no. 13).

**Pengujian**: `tests/LogTerminalServerProxyTest.php` (proksi log/terminal, chunked & sesi tidak ditutup saat drop, `run` diproksi ke agent), `tests/AgentTerminalControllerTest.php`, `tests/AgentLogControllerTest.php`, `tests/TerminalStreamContractTest.php`, `tests/SigchldGuardTest.php`.

## 5.29 File Manager per Server (F3b)

File manager container app di server `kind=agent` berjalan **di agent** — Docker Engine host control plane tidak pernah disentuh untuk app remote (plan §3 butir 4). Control plane hanya mem-proxy (`FileController::withAgent()` → `AgentDeployer::file*()`); `null` ⇒ jalur lokal lama, sedangkan konfigurasi agent yang cacat **melempar** `AgentError` (tidak ada fallback ke server lokal).

| Route dashboard (control plane) | Route agent | Ability |
|---|---|---|
| `GET /api/apps/{id}/files` | `GET /files/list` | `files` (operator+) |
| `GET /api/apps/{id}/files/read` | `GET /files/read` | `files` |
| `GET /apps/{id}/files/download` | `GET /files/download` | `files` |
| `POST /apps/{id}/files/{write,mkdir,rename,delete,move,upload,extract}` | `POST /files/{write,mkdir,rename,delete,move,upload,extract}` | `files` |

- **Otorisasi sebelum efek samping**: `FileController::requireApp()` (`AppStore::find` + `AppAccess::require('files', …)`) → app tak berhak = **404** (`AppAccessDenied`), dijalankan **sebelum** panggilan agent/Engine.
- **Route agent** hanya didaftarkan di `RAMES_MODE=agent` (di mode dashboard **tidak ada**) dan tertutup `AgentAuthMiddleware` (token + timestamp + nonce + signature). `app_id` ikut di query (GET) / body (POST) — app dibaca dari **proyeksi agent**, bukan tebakan pemanggil.
- **Bentuk respons UI tidak berubah** (JS lama tetap jalan): envelope agent `{code:0,data}` diteruskan apa adanya; galat **domain** memakai HTTP **200** + `{code:<status>,msg}` sehingga kode 409 (container berhenti), 413 (terlalu besar), 415 (biner), 404 **sama dengan jalur lokal**. **Pengecualian**: `GET /files/download` memakai **status HTTP nyata** (409/413/404) + envelope `{code,msg}` supaya control plane bisa membedakan "respons ini JSON galat" dari "respons ini isi berkas" — tidak pernah ada byte galat yang mengalir sebagai berkas.
- **Batas & keamanan (library yang sama dengan jalur lokal)**: path/nama divalidasi `PathGuard` sebelum `docker exec`/`docker cp`; arsip `.zip`/`.tar.gz` diekstrak lewat `ArchiveGuard` (**zip-slip** & symlink escape ditolak, batas `MAX_ENTRIES`/`MAX_EXTRACT_BYTES`); editor teks `TextContent::MAX_TEXT_BYTES` = 2 MiB & tolak biner (415); listing dipotong `ContainerFiles::MAX_LIST_ENTRIES` = **5000** entri (`truncated`, jaring pengaman kedua di control plane); transfer berkas dibatasi `AgentDeployer::MAX_TRANSFER_BYTES` = **64 MiB** (ditegakkan di agent **dan** sebagai jaring pengaman kedua di `FileController::streamDownload()`).
- **Streaming & kebersihan**: unduhan agent → klien dialirkan **chunked** via `Timer` (`PROXY_TICK`, `Webman\Http\Response` + `Chunk`, tanpa buffer penuh); unggahan mengirim body biner mentah (field kecil di query). Berkas temp (agent & control plane) selalu dibersihkan (`ContainerFiles::scheduleCleanup()`/`cleanup()`), termasuk saat 413.
- **Audit** operasi berkas (jalur lokal & agent) ditulis di control plane saja (`runtime/logs/files/`, identitas pelaku hanya ada di sana); agent tidak menulis audit.
- Endpoint agent tak dikenal (app di luar proyeksi / container tak dikenal) ⇒ HTTP **404** `{code:1,error,reason}` agar `AgentClient` memetakannya ke `AgentError('not_found')`.

**Pengujian**: `tests/AgentFilesControllerTest.php`, `tests/FileMonitorServerProxyTest.php` (proksi & isolasi host lokal), `tests/FileControllerEnvelopeTest.php`, `tests/FileArchiveGuardTest.php`, `tests/ContainerFilesRootUserTest.php`.

## 5.30 Monitoring per Server (F3c)

`GET /api/monitor/overview` mengumpulkan **server yang boleh dilihat user** — admin semua server, non-admin hanya server yang menaungi minimal satu app yang ia lihat. Kunci lama (`host`/`containers`/`totals`/`error`/`scope`/`at`) tetap milik server **lokal** sehingga `public/js/monitor.js` berjalan apa adanya; agregat per server ditambahkan di kunci baru **`data.servers[]`**.

| Entri `servers[]` | Sumber |
|---|---|
| lokal (`kind:'local'`, `status:'online'`) | hasil `ResourceCollector::collect()` jalur lama (`/proc` host ini + Engine host ini); hanya app berserver lokal yang dipetakan ke project host ini |
| agent (`kind:'agent'`) | `AgentDeployer::hostUsage()` (`GET /system/host-usage`; CPU/memori/load/uptime **dan storage server** `/proc`+`statvfs` server itu) + `AgentDeployer::containerStats()` (`GET /monitor/containers`) — metrik dibaca **di server itu** |

- **Bentuk entri**: `{id,name,kind,status,enabled,host,containers,totals,error,at}`. Penyaringan hak akses sisi control plane (`remoteRows()` mengikuti aturan `ResourceCollector`): container milik app → hanya bila app boleh dilihat user; container "eksternal" (tanpa project) → hanya admin; project bukan app dashboard → tidak pernah.
- **Satu server rusak tidak mematikan halaman**: server agent yang mati/token ditolak/respons tak sesuai kontrak ⇒ entri ber-`status:'offline'` + `error` tersanitasi (`AgentError::sanitize()`, token tidak pernah muncul), **tanpa** melempar — halaman `/monitor` tetap HTTP 200.
- **Metrik host control plane tidak pernah dipakai untuk server agent** (kebalikannya juga): `MonitorController::dockerClient()`/`localApps()` khusus lokal, `AgentDockerController` khusus server agent.
- `GET /api/monitor/host` (dipoll tiap beberapa detik) **tetap server lokal saja** — memanggil seluruh agent di sini akan membanjiri jaringan; metrik per server disajikan `overview` (saat halaman dibuka/di-refresh).
- **`data.servers[]` disaring di SERVER, bukan di JS** (keputusan §9.3, `ServerAccess::visibleServers()`): admin menerima semua server; non-admin hanya server yang menaungi app yang boleh ia lihat (`AppAccess::visible()`), tanpa app terlihat ⇒ daftar **kosong** (fail-closed). **WAJIB — grant `server_select` tidak membuka metrik host**: server yang hanya "terlihat" karena grant/allowlist tanpa satu pun app user di sana **tidak** boleh dirakit/dihubungi `overview` (rantai filter app terlihat diterapkan **sebelum** entri server dibuat). Server yang tidak boleh dilihat **tidak pernah dihubungi** (entrinya tidak dirakit) sehingga id/nama/kind/status/host-nya tak mungkin bocor lewat JSON. Penyaringan di `public/js/monitor.js` hanya lapisan kedua (UX), bukan pengaman.
- **UI `/monitor` (F4)**: `app/view/monitor/index.php` + `partials/panel.php` merender kartu ringkasan **per server** dari `data.servers[]` (badge `online`/`offline`/`unknown`/`nonaktif`, tabel container per server) — admin juga melihat tautan registry `/servers`; non-admin tidak. Kolom **Disk** tabel itu memuat **dua baris**: volume Docker terpakai (hanya dihitung untuk server lokal, dari `GET /api/volumes/usage`) dan **storage server** (terpakai / total · sisa, dari `host.disk_*` masing-masing server). `public/js/monitor.js` (kontrak `data-is-admin`) menyaring barisnya sebagai lapisan kedua.
- **Belum**: metrik historis/grafik per server (polling `host` tetap lokal saja).

**Pengujian**: `tests/FileMonitorServerProxyTest.php` (agregat `servers[]`, offline tidak menggagalkan halaman, penyaringan per role, **non-admin tak menerima & tak menghubungi server asing**, endpoint host tetap lokal), `tests/MonitorServerGrantTest.php` (grant/allowlist tanpa app terlihat **tidak** membuka metrik host; setelah ada app terlihat ⇒ server muncul), `tests/AgentDockerControllerTest.php` (`/proc` server agent sendiri, Engine agent sendiri), `tests/MultiServerViewTest.php` (render kartu server + `monitor.js`).

## 5.31 Database/Adminer, Network & Volume per Server (F3d)

Resource Engine bersifat **per server** (satu daemon = satu himpunan container/network/volume). Karena itu `/database` dan `/networks` membaca targetnya dari server yang bersangkutan, bukan dari host control plane.

| Control plane (route) | Agent (route, mode `RAMES_MODE=agent`) | Sumber kebenaran |
|---|---|---|
| `GET /database` (kolom **server** per baris) | `GET /database/containers` | `AgentDeployer::dbContainers()` → `DbContainerDetector` di server itu |
| `ANY /database/{container}/adminer[/{path:.*}]` | `ANY /adminer/{container}[/{path:.*}]` | helper Adminer (`AdminerHelper`/`AdminerProxy`) dijalankan **di server itu** (helper tanpa port publik) |
| `GET /networks`, `GET /networks/{id}`, `POST /networks/*` | `GET /networks`, `GET /networks/{id}`, `POST /networks/*` | `NetworkManager`/`DockerClient` Engine server itu |
| `GET /volumes`, `POST /volumes/purge` (baris dari server yang boleh dilihat user; **purge hanya Engine host ini** — volume agent ditolak fail-fast, §5.35) | `GET /volumes?project=` | `NetworkManager`/`DockerClient` Engine server itu |

- **Server app mana yang dipakai ditentukan oleh data, bukan input user**: proxy Adminer mencari app pemilik container (`DatabaseController::findOwningApp()` → ability `database`, penolakan **404**) lalu membaca `app.server_id`; app server lokal memakai `AdminerProxy` lokal, app server agent di-proxy ke agent itu. Tidak ada parameter `?server=` di jalur Adminer, jadi tidak ada cara user memaksa helper server lain.
- **Body permintaan diteruskan mentah** (`multipart/form-data`, unduhan, unggahan `.sql`) — proxy tidak mem-parse/menulis ulang body, hanya mengganti host tujuan; header browser disaring daftar-putih dan `X-Forwarded-Prefix` **hanya** boleh datang dari control plane (bukan dari klien). **Jar cookie** (state login Adminer) hidup **di sesi control plane** dan dititipkan ke agent per request lewat header `X-Rames-Adminer-Jar` (base64 JSON) — agent tetap tanpa sesi/basis data user, dan header `X-Rames-Adminer-*` tidak pernah keluar ke browser.
- **Network & volume hanya bermakna dalam satu server**: `NetworkController` membandingkan `serverKeyOf()` app dengan server network; connect/delete container lintas server ditolak dengan pesan jelas (`assertContainerServer()`) — bukan "network tidak ditemukan".
- **Volume project per server**: daftar volume sebuah project dibaca lewat `DeployerInterface::getProjectVolumes()` — `AgentDeployer` memakai route agent `GET /volumes?project=` (filter label `com.docker.compose.project` dijalankan Engine **server itu**, jadi hasilnya sama dengan `LocalDeployer`; dipakai modal konfirmasi delete app di server agent), dan halaman `/backups` menggabungkan volume lokal dengan **volume backup server agent** (`AgentDeployer::backupVolumes()` → agent `GET /backups/volumes`, §5.32). **Per server (kini terlihat)**: `/volumes` (`VolumeController::collectAgentVolumes()`) membaca **seluruh** volume ber-label compose server agent lewat `AgentDeployer::backupVolumes()` (`GET /backups/volumes`) — bukan per project — sehingga volume **yatim** (project/app sudah dihapus) ikut tampil; `orphaned` diputuskan control plane dari `apps.json` server itu (bukan medan `orphaned` agent). Purge tetap **lokal-only** (GOTCHA no. 23).
- **Penjaga antar-fase**: op yang belum server-aware **ditolak eksplisit** (mis. `appArtifactDirOrFail()` untuk container-name/limits/external-network app agent), bukan dieksekusi di server lokal. **Env sudah server-aware** (§5.37): app agent disimpan sebagai metadata + job `apply_env` (control plane tidak menulis `database/env/*`), upload `.env` review-only, import `.env.example` ditolak dengan pesan akurat karena berkas itu hanya ada di checkout agent.

**Pengujian**: `tests/DatabaseAdminerServerProxyTest.php`, `tests/AgentAdminerControllerTest.php`, `tests/AdminerProxyForwardTest.php`, `tests/AdminerForwardContextTest.php`, `tests/AdminerHelperTest.php`, `tests/AdminerNetworkTtlTest.php`, `tests/CsrfExemptAdminerProxyTest.php`, `tests/NetworkServerScopeTest.php`, `tests/DbContainerVisibilityTest.php`, `tests/DatabaseIndexServerScopeTest.php`, `tests/AppPortsServerScopeTest.php`.

## 5.32 Data per Server (F4): Backup / Restore / Dump & UI

Op berat data (restic, helper container, dump logis) berjalan **di server yang memiliki volume itu**. Control plane hanya mengirim job & menyimpan riwayat.

| Peran | Kelas / CLI | Catatan |
|---|---|---|
| UI & otorisasi | `BackupController` (`/backups`, `POST /backups/run\|restore\|db-dump`, `GET /api/backups/status\|snapshots`) | ability `backup` = **operator**, `restore` = **owner** (`BackupAccess` → `AppAccess`, penolakan **404**); volume yatim admin-only |
| Worker control plane | `cli/backup.php run\|restore\|db-dump … <serverId>` | volume lokal ⇒ jalur lama; `serverId` non-lokal ⇒ `BackupDispatcher` (hook uji `RAMES_BACKUP_DISPATCHER_CLASS`) |
| Router | `BackupDispatcher` | memilih job agent vs jalur lokal; menolak **sebelum efek samping** |
| Job agent | `POST /jobs` op `backup_run\|restore\|db_dump` (`AgentJobController::DATA_OPS`) → worker `cli/deploy.php` di server itu → `BackupJobRunner` | kredensial **server itu** (env-file 0600); riwayat **tidak** ditulis di agent |
| Registry | `BackupRegistry::scopeKey()` = `<server_id>::<volume>` (server lokal tetap nama volume) | dua server dengan volume bernama sama **tidak bertabrakan**; kolom turunan `server_id` disimpan **di dalam** entri JSON — **tanpa migrasi skema** |

- **Payload job data sangat sempit**: hanya `op`, `volume`, `snapshot`/`trigger`, `app_id`, `ref`, `actor_id`, `preserve_volumes`, `domain`, dan dokumen `app` (metadata tanpa kredensial). **Tidak ada** kredensial restic/S3/passphrase di payload, rekaman job (`runtime/agent-jobs/`), log, atau `argv` — kredensial tetap di `database/restic/*` + env server itu (`CredentialEnvFile` 0600).
- **Aman lintas server** (semua dicek di `BackupDispatcher`): server tak dikenal/`enabled:false` ⇒ ditolak; volume tidak ada / tidak terhubung app (yatim) ⇒ ditolak; app pemilik volume terdaftar di `server_id` **berbeda** ⇒ ditolak ("mencegah backup/restore di server yang salah"); dispatcher **tidak pernah** dijalankan untuk server lokal (kesalahan pemanggil).
- **`VolumeStateGuard` tetap berlaku di jalur agent**: strategi `snapshot` dengan policy `stop` memanggil `assertStopped()` (tidak ada container yang me-mount volume) sebelum `restic backup`, dan `start` dikembalikan di `finally` — aturan yang sama dengan jalur lokal karena `BackupJobRunner` memakai `VolumeBackupService` bawaan server itu.
- **Fail-fast 422, bukan setengah jalan (yang memang belum didukung)**: `restore-archived` untuk volume agent kini **didukung** — job tingkat server `restore_archived` di server itu (§5.34, payload `snapshot`+`target_name`, `VolumeArchiveRestore` + `VolumeStateGuard`); yang masih **422** adalah `GET /api/backups/archive/snapshots` & `GET /backups/archive/sql` (unduh `.sql` arsip) untuk `server_id` non-lokal — arsip & repo restic volume agent hidup di server itu, dibaca lewat `GET /api/backups/snapshots?volume=…&server_id=…` (→ `AgentDeployer::backupSnapshots()` → agent `GET /backups/snapshots`) atau di-dump dengan job `db_dump`, bukan dari repo control plane yang bisa punya volume bernama sama.
- **Kapabilitas sebelum spawn**: `BackupController::assertAgentSupports()` memeriksa `capabilities` server — server yang **melaporkan** capability **tanpa** op data ⇒ **422** tanpa spawn worker; server yang belum pernah melaporkan capability ⇒ operasi diteruskan (keputusan di agent: op tak dikenal ⇒ **501 `unsupported`**) — selaras `DeployWorkerLauncher::MODES` ≡ `AgentJobController::OPS` ≡ daftar mode `cli/deploy.php` (tak ada op "senyap").
- **UI F4**: `/monitor` merender kartu **per server** (§5.30); pemilih server di `/networks` tersedia untuk admin **atau** pemegang grant `server_select` (daftar disaring `ServerAccess::visibleServers()`; non-admin di luar jangkauan ⇒ 404 fail-closed, §5.31); `/database` merender **kolom Server** (badge `agent` + nama server untuk baris dari agent, kosong untuk baris lokal) dan tetap menyaring baris milik app yang boleh dilihat user; detail app merender **badge server** (`<span class="badge text-bg-info">Server: <nama></span>`, hanya untuk app server agent) dan tab Info menampilkan baris `Server` (`agent <nama>` vs `lokal`).
- **Mendarat setelah F4 (F4 lanjutan, §5.33–§5.35)**: **jadwal fan-out per server** — timer host tetap `cli/backup.php run` tanpa `serverId`, tetapi run itu kini memfans-out volume bertanda `scheduled` milik server agent sebagai job `backup_run` ke server pemiliknya (satu clock di control plane; `agent/install.sh` **tidak** memasang timer), dengan exit code per volume/server; **unduh `.sql` bertahap + retensi staging** (agent `GET /backups/dump` + `DumpStaging::prune()`, 3 knob config); **restore arsip volume server agent** (job `restore_archived`, `VolumeArchiveRestore` + `VolumeStateGuard`); **template pull per server** (`template_pull` di agent); **self-update agen + versi/kapabilitas** (`AgentVersionGate`, `POST /servers/{id}/agent-update`, gerbang `control_plane_version` di sisi agen); **`Run` (one-shot) app agent** (agent `POST /terminal/run`, bukan lagi 501 — GOTCHA no. 13); **halaman `/volumes` & `/apps` sadar-server** (§5.35). **Sudah mendarat lebih dulu**: **metering & tagihan per server (F4b)** — §5.18 (ii).
- **Sisa yang masih terbuka (F4)**: **penghapusan/purge volume server agent** belum punya op/job di agent ⇒ `purge_orphans` tetap lokal-only + laporan eksplisit, dan baris agent `can_purge=false`; baris volume agent menampilkan `—` untuk driver/mountpoint/dibuat/ukuran (kontrak `GET /backups/volumes` tidak menginspeksi volume per baris); **risiko higienitas sisa** — pesan galat yang ditulis worker (`cli/deploy.php` → `apps.error`/log deploy) dapat memuat `AgentError` mentah, `AgentTemplatePull::panel()['log_tail']` menampilkan log job apa adanya, dan `AppStopper` menulis galat stop agent ke log billing.

## 5.33 Versi & Kapabilitas Agen (`AgentVersionGate`) + Perbarui Agen dari Dashboard

Satu kode, satu image, **dua peran runtime** (§3) — tetapi sebuah agen bisa tertinggal beberapa rilis. Gerbang versi/kapabilitas menolak ketidakcocokan **sebelum efek samping apa pun**, di kedua arah:

| Arah | Nilai | Penegak |
|---|---|---|
| Control plane terlalu tua untuk agen | `GET /version['min_control_plane_version']` disimpan di baris server (`min_control_plane_version`) | `AgentVersionGate::check($server,$op)` ⇒ `errors` (dipakai `ServerController::agentUpdate` ⇒ **400**) & `assertCompatible()` ⇒ `AgentError` `unsupported`; sisi **agen**: `assertControlPlaneCompatibleWithAgent($jobPayload['control_plane_version'])` ⇒ tolak (versi **kosong** pun ditolak) |
| Agen terlalu tua untuk control plane | `MIN_AGENT_VERSION` (`AgentVersionGate`) | `check()` ⇒ `errors`; UI menandai baris "tidak kompatibel" + tombol Perbarui agen **disabled** |
| Op tidak ada di `capabilities` agen | `capabilities` hasil Test connection (tersimpan di baris server; = `AgentJobController::OPS` = `DeployWorkerLauncher::MODES`) | `supports()`/`check($server,$op)` ⇒ `errors`; **capabilities diutamakan atas string versi**; capabilities **kosong** = "belum diuji" ⇒ hanya `warnings` (keputusan akhir di agen, `POST /jobs` ⇒ **501 `unsupported`**) |

- **Satu angka versi**: `AgentVersionGate::CODEBASE_VERSION` (kini `0.1.0`) — dirujuk `AgentController::VERSION`/`MIN_CONTROL_PLANE_VERSION` dan dikirim control plane sebagai `control_plane_version` di payload job `self_update` (`ServerController::agentUpdate`). Jangan menyalin angkanya ke tempat lain.
- **Perbarui agen dari dashboard**: `POST /servers/{id}/agent-update` (admin-only ⇒ non-admin **404**; JSON) → `AgentVersionGate::check()` **dulu** (tidak kompatibel ⇒ 400, tanpa job) → job tingkat server `self_update` target `agent` di server itu (payload `update_mode` + `control_plane_version`, lihat §5.34). Server lokal ditolak 400 (dashboard diperbarui lewat Config → tab Update). UI `/servers`: kolom **Versi & kompatibilitas** (badge `kompatibel`/`tidak kompatibel`/`belum diketahui`) + tombol **Perbarui agen** per baris (`public/js/server.js`, dinonaktifkan bila tidak kompatibel).
- Pesan galat gerbang **tidak pernah** memuat token/`base_url` (hanya nama + id server, `AgentVersionGate::label()`).
- **Endpoint non-job tidak ikut `capabilities`**: `capabilities` = op job (`AgentJobController::OPS` = `DeployWorkerLauncher::MODES`); `POST /nginx/check` & `POST /apps/check` tidak dilaporkan di sana, jadi ketiadaannya pada agent lama dideteksi murni dari **HTTP 404** (preflight create app ⇒ `AgentError::NOT_FOUND` **dilewati**, §5.22; GOTCHA §8 no. 36). Jangan menambahkannya ke `capabilities` tanpa mengubah deteksi itu.

**Pengujian**: `tests/AgentVersionGateTest.php` (kapabilitas vs versi, dua arah, pesan tanpa kredensial, tidak ada op "senyap"), `tests/ServerControllerTest.php`, `tests/ServerViewTest.php`, `tests/CliDeployServerOpsTest.php` (gerbang sisi agen di worker), `tests/MultiServerViewTest.php` (badge/tombol di `/servers`).

## 5.34 Op Tingkat Server di Agen, Jadwal Fan-out, Retensi Staging & Unduh Bertahap

**Op tingkat server** = mode `cli/deploy.php` yang **tidak terikat satu app** (`DeployWorkerLauncher::SERVER_OPS` = {`template_pull`, `self_update`, `restore_archived`}, semuanya anggota `MODES` ⇒ otomatis ikut `AgentJobController::OPS` & `capabilities`). Karena tanpa app, slot `argv[1]` berisi **target** (slug template / `agent` / nama volume arsip) dan blok ini berjalan **sebelum** pemuatan app di store:

| Op | Target | Yang dijalankan **di server itu** |
|---|---|---|
| `template_pull` | slug template | `TemplatePullService::preflight()` (slug dikenal, template valid, ada image, tidak ada run berjalan) lalu worker `cli/pull.php` **sinkron** (`TemplateCatalog` + `docker pull` per image) ⇒ image masuk daemon **server itu**; preflight gagal ⇒ job 400 tanpa `docker pull` |
| `self_update` | `agent` (tetap) | `UpdateService` (helper container **di luar** compose project server itu) dengan mode dari payload (`update`\|`rollback`); hanya berlaku di `RAMES_MODE=agent` (mode dashboard ⇒ tolak: dashboard diperbarui lewat Config → tab Update); prasyarat `preflight()` gagal ⇒ fail-closed tanpa start; gerbang versi sisi agen (§5.33) diperiksa lebih dulu |
| `restore_archived` | nama volume **arsip** | `VolumeArchiveRestore` (`docker volume create` → `restic restore` → hapus volume target bila gagal) dengan `VolumeStateGuard` tetap ditegakkan; payload wajib `snapshot` + `target_name` (keduanya divalidasi library yang sama dengan jalur lokal) |

**Route agent baru** (mode `agent` saja, `config/route.php`): `GET /backups/dump?volume&offset&limit` (potongan berkas `.sql` staging **server itu** + header `X-Rames-File`/`X-Rames-Offset`/`X-Rames-Size`/`X-Rames-Eof`; `limit` dipagari `DumpStaging::MAX_READ_BYTES`; belum ada dump ⇒ **404**, bukan 500), `POST /terminal/run` (perintah **satu-kali** lewat `DockerExec::runCommand()` yang sama dengan jalur lokal — bukan sesi terminal, jadi tidak ada sesi/FIFO tertinggal). Route dashboard: `GET /backups/dump/sql?volume&server_id` (ability `backup` = operator; `server_id` **satu pintu** `BackupController::findTarget()` — volume server agent diunduh lewat potongan dari server itu, volume lokal dari staging host ini; `Content-Disposition` attachment).

**Jadwal backup fan-out per server — satu clock di control plane.** Timer host (`host/systemd/volume-backup.timer`) tetap menjalankan `cli/backup.php run` **tanpa** `serverId`; yang berubah adalah artinya: run tanpa daftar volume memanggil `BackupSelection::scheduledByServer()` sehingga volume **server lokal** dijalankan `VolumeBackupService` di host itu, sedangkan volume **server agent** dikirim sebagai job `backup_run` (trigger `schedule`) ke server pemiliknya lewat `BackupDispatcher`. `agent/install.sh` **tidak** memasang timer apa pun (sengaja: satu clock, satu tempat melihat hasil). **Exit code `cli/backup.php run` = hasil nyata per volume/server**: sukses job agent ⇒ **0** walau Engine host lokal tidak terbaca (cron jangan menandai backup agent gagal), dan sebaliknya kegagalan agent ⇒ non-nol walau jalur lokal sukses.

**Retensi staging dump (3 knob)** — berlaku di sisi mana pun yang menjalankan dump (host maupun agent), dipanggil `BackupJobRunner` setelah dump sukses (`DumpStaging::prune()`): `VOLUME_BACKUP_DUMP_KEEP` (`volume_backup_dump_keep`, default 5 = jumlah dump terbaru per project), `VOLUME_BACKUP_DUMP_MAX_AGE_DAYS` (`volume_backup_dump_max_age_days`, default 7), `VOLUME_BACKUP_DUMP_DOWNLOAD_MAX_BYTES` (`volume_backup_dump_download_max_bytes`, default 128 MiB = plafon satu unduhan `.sql`). `prune()` tidak pernah menghapus berkas di luar root staging.

## 5.35 Halaman `/volumes` & `/apps` Sadar-Server

- **`/apps`**: kolom **Server** (badge `agent` + nama server; `lokal` untuk host ini) + filter `?server=<id>` — pilihan filter diambil dari `ServerAccess::visibleServers()` sehingga **non-admin tidak pernah melihat/memilih server di luar jangkauannya** (server yang menaungi app terlihat + server grant `server_select`; tanpa keduanya: tanpa pemilih server sama sekali); tab (scope mine/all) mempertahankan filter. Ditambah **filter query-string `?name=`/`?domain=`/`?owner=`** (SPECS §8e) lewat `AppFilter`: digabung **AND** dengan `scope`/`server` (filter diterapkan sebelum hitung tab ⇒ `counts` ikut menyempit), `?owner=` **hanya dihormati untuk admin** (non-admin diabaikan total), id owner di luar `user_names()` diabaikan; tautan tab mempertahankan filter, tombol **Reset** membuang filter sambil menyisakan `scope`/`server`.
  - **Toolbar filter = satu form GET.** Seluruh kontrol (Server/Nama/Domain/Owner + hidden `scope`) berada dalam **satu** `<form class="card" method="get" action="/apps" aria-label="Filter daftar app">` di bawah tab scope — bukan dua form berdampingan; satu tombol **Terapkan**. Berbasis query string (GET, **tanpa CSRF** — bukan POST) sehingga berfungsi penuh tanpa JS & URL tetap bisa dibagikan; aksi utama **`+ Create App`** tetap di `page-head` (di luar form).
  - **Lebar kolom adaptif.** Jumlah field yang benar-benar dirender (`$__filterFieldCount` di `app/view/app/index.php` = ada pilihan Server?1:0 **+2** (Nama+Domain) **+** admin?1:0 (Owner)) memilih `$__filterCol`: 2 field ⇒ `col-6 col-md-6 col-xl-4`, 3 ⇒ `col-6 col-md-4 col-xl-3`, 4 ⇒ `col-6 col-md-3 col-xl-2` — pada `md` tiap kombinasi mengisi **12/12** kolom (tanpa celah kanan) dan pada `xl` menyisakan ruang sehingga grup tombol (`col-12 col-xl-auto ms-xl-auto`) muat **sebaris**.
  - **WAJIB — non-admin tetap membawa `?server=`.** Non-admin **tanpa grant** tidak pernah mendapat pemilih server (`$serverOptions === []`), tetapi `?server=<id>` bisa datang dari tautan/bookmark yang dibagikan admin. Karena semua kontrol kini satu form, nilai itu **wajib** dibawa lewat **input tersembunyi kondisional** `name="server"` (`$__serverFilter !== '' && $__serverOptions === []`); tanpa itu menekan **Terapkan** membuang filter server padahal tautan tab tetap mempertahankannya (tidak konsisten). Param `server` **DILARANG** terkirim dua kali (select + hidden) — itulah sebabnya input tersembunyi **kondisional** (hanya saat select tidak dirender). Tombol **Reset** muncul hanya bila ada filter aktif **atau** `?server=` terisi, dan menyisakan `scope`+`server` (`$__resetUrl`).
- **`/volumes`**: baris datang dari **setiap server yang boleh dilihat user** (lokal dari Engine host ini, agent dari `AgentDeployer::backupVolumes()` server itu — daftar **per server**, bukan per project, sehingga volume **yatim** ikut terlihat), kolom **Server** menandai asalnya. **Penyaringan satu pintu**: `VolumeController::collectRows()` menyaring per project yang boleh dilihat user — non-admin: server agent tanpa satu pun app terlihat **tidak dihubungi sama sekali** (fail-closed, bukan "semua lalu disaring"); **admin selalu menghubungi setiap server agent** (server yang seluruh app-nya sudah dihapus justru satu-satunya tempat volume yatim berada). `orphaned` diputuskan control plane dari `apps.json` server itu. Server tak terjangkau ⇒ **satu pesan per server** (`serverErrors`, diredaksi `AgentError::sanitizeForServer()`) dan halaman **tetap tampil**. Agent lama tanpa `GET /backups/volumes` (404/`unsupported`) memakai **jalur mundur** per project (`GET /volumes?project=`) — volume app tetap tampil, yatim tidak.
- **Purge volume fail-fast**: `POST /volumes/purge` admin-only. Volume milik **server agent** ditolak **sebelum efek samping apa pun** (`agentVolumeOwners` dipetakan lebih dulu) sehingga tidak ada volume lokal yang terhapus karena salah atribusi server; `purge_orphans=1` menyasar **hanya** Engine host ini dan melaporkan yatim server agent secara eksplisit (penghapusan volume agent belum punya op/job di agent). Baris agent selalu `can_purge=false`; satu-satunya cara membersihkannya adalah di server itu sendiri sampai op `volume_rm` tersedia.
- **Baris agent menampilkan `—`** untuk driver/mountpoint/dibuat/ukuran: kontrak `GET /backups/volumes` melaporkan `{name, project, app_id, orphaned}` — tidak ada inspeksi volume per baris (mahal & butuh endpoint baru). Itu batas yang disengaja, bukan data hilang yang bisa ditebak; jangan mengambilnya dari Engine host ini.
