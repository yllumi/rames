# 6. Keputusan Teknis Penting

> Bagian dari [dokumentasi arsitektur](../ARCHITECTURE.md) · Spesifikasi: [SPECS.md](../SPECS.md) · Panduan operasional: [DETAILS.md](../../DETAILS.md)

- **Anti command injection**: `ProcessRunner` memakai bentuk **array + `bypass_shell`** (langsung `execve`, tanpa shell) — lebih ketat daripada string + `escapeshellarg`.
- **Hybrid Docker**: CLI `docker compose` untuk orkestrasi (up/down/build), `DockerClient` (Engine API via unix socket) untuk operasi baca status. Ini menghindari SDK yang tak punya semantik `compose up`.
- **Overwrite port via `!reset`**: solusi atas perilaku merge daftar `ports` docker compose; butuh compose **v2.6+**.
- **JSON in-place write (cache runtime)**: `JsonStore::update()` (kini hanya untuk cache runtime, §4.5) menulis pada file yang sudah ada (`fopen c+`) sehingga ownership file tetap milik host — nyaman saat file di-share host↔container.
- **SQLite untuk data domain, JSON untuk cache** (§5.19): data app/user/billing/seleksi+riwayat pindah ke satu berkas SQLite (named volume `rames`) dengan `data` = dokumen JSON + kolom turunan terindeks; mutasi atomik `BEGIN IMMEDIATE`. Cache yang bisa dibangun ulang (`check.json`, `catalog.json`/`status.json`/`runs/*.json`, state Adminer, state backup DB) tetap JSON agar tidak menambah beban tulis DB.
- **Kunci cache koneksi = identitas berkas (`realpath#dev:ino`)** (§5.19): handle PDO di-cache per proses per berkas; menyertakan inode membuat berkas yang **diganti** (restore/rename atomik) otomatis dianggap berbeda → koneksi dibuka ulang + skema diverifikasi ulang, sekaligus mencegah worker memakai handle inode basi setelah restore.
- **Impor legacy sekali, bukan migrasi dua arah otomatis** (§5.19): `JsonImporter` menyalin `database/*.json` ke SQLite **sekali** (flag `kv.legacy_imported_at`), berkas JSON lama tidak dihapus; rollback eksplisit lewat `php cli/db.php export-json`. Mencegah dua sumber kebenaran berjalan bersamaan.
- **Backup DB via `VACUUM INTO` + mutex `flock`** (§5.19): snapshot konsisten tanpa menghentikan worker; `<backup_dir>/.lock` (non-blocking) menyerialkan snapshot/prune/restore — run yang tumpang tindih **dilewati** (`skipped=busy`), bukan error; retensi meniru `restic forget --keep-*`.
- **Domain parking: config Nginx berkas terpisah `_parked_{id}.conf`** (§5.38): regenerate config app (deploy/rebuild, set subdomain, custom domain) hanya menulis berkas app, sehingga config parkir tidak pernah tertimpa atau terhapus. Prefiks `_parked_` dipilih karena nama app **tidak boleh** berawalan `_` — ruang nama berkas dijamin bebas bentrok tanpa tabel pemetaan.
- **Domain parking: halaman `html` disajikan Nginx langsung dari `root`, bukan lewat proxy dashboard** (§5.38): berkas statis `{PARKED_ROOT}/{id}/index.html` dibaca Nginx host (satu direktif `root` + `try_files`), sehingga tidak ada request ke dashboard, tidak ada worker PHP yang sibuk, dan halaman tetap hidup walau container dashboard berhenti. Konsekuensinya `PARKED_ROOT` harus terlihat & terbaca **Nginx host** (bukan hanya container dashboard).
- **Domain parking: transaksi "uji dulu + rollback" di manager** (§5.38): `nginx -t` memvalidasi **seluruh** config host, jadi berkas `_parked_*.conf` invalid yang tertinggal memblokir reload semua app + renewal SSL. Karena itu urutan simpan → tulis → reload dibalik dengan rollback eksplisit dan `reload()` hanya dipanggil **sekali** setelah semua berkas ditulis; kegagalan tulis config tidak pernah diikuti reload.
- **Domain parking: `www` = entri terpisah, bukan alias** (SPECS §8j): `www.contoh.com` punya baris `parked_domains`, id, direktori konten, dan config sendiri; opsi `add_www` hanya pintas create (dua entri identik), sehingga mengubah/menghapus salah satu tidak diam-diam mengubah yang lain. Tidak ada sinkronisasi otomatis (GOTCHA no. 46).
- **Domain parking: `PARKED_ROOT` wajib absolut, tanpa `$`/`..`, dan sama persis di host** (§5.38): direktif `root` dieksekusi Nginx **host**, bukan container; path relatif di-resolve relatif prefix Nginx ⇒ 404 senyap, dan `$` diekspansi sebagai variabel Nginx. `ParkedDomainContent` menolak root relatif/ber-`..` dan `ParkedNginxConfig::assertPath()` menolak karakter yang bisa memecah direktif — validasi terjadi **sebelum** berkas/config ditulis.
- **Satu halaman `/domains`, dua tab** (§5.38, SPECS §8j.3): tabel domain app + parkir dan status SSL-nya tidak boleh dipecah ke dua halaman (duplikasi baris/logika). `GET /domains` + `GET /api/domains/status` terbuka semua user login — baris app disaring `AppAccess::visible()`; baris parkir + seluruh aksi pengelolaan/SSL parkir admin-only (404). `GET /ssl` tinggal alias **302**; jangan menambah logika domain di sana (GOTCHA no. 50).
- **SSL app per slot** (§5.6/§5.6b): `ssl_*` = subdomain (termasuk saat subdomain hanya redirect), `custom_ssl_*` = custom domain. Dua baris `/domains` punya tombol/status sendiri; blok 443 subdomain redirect memakai **cert subdomain**, bukan cert custom domain, dan target redirect tetap mengikuti `custom_ssl_status` (GOTCHA no. 48).
- **SSL parkir per entri** (SPECS §8j.6a): field `ssl_*` hidup di dokumen `parked` (tanpa kolom/migrasi baru), aktivasi lewat worker detached `cli/parked-ssl.php`, config `_parked_*.conf` dirender ulang dengan blok 443 **hanya** bila cert benar-benar ada — config parkir tetap terpisah dari config app.
- **Kegagalan config/reload pasca-issue = `failed`, bukan `active`** (SPECS §8j.6a): UI hanya menampilkan tombol Retry untuk status `failed`; menyimpan `active` + `error` akan menyembunyikan jalan pemulihan. `ssl_expires_at` cert yang baru **dipertahankan** agar Retry/reconcile berikutnya tidak perlu menerbitkan ulang (`certbot --keep-until-expiring`).
- **Akrual menuntut bukti container hidup di server app (F4b)**: `UsageProbe` membaca bukti **per server** (server `local` ⇒ `DockerClient::listContainers()`; server agent ⇒ `AgentDeployer::containerStats()` → `GET /monitor/containers`), bukan `status` di control plane. Bila satu server tak terjangkau, akrual interval itu **dilewati** dan alasannya dicatat — bukan ditebak: menagih tanpa bukti (over-count) lebih berbahaya daripada under-count. Akrual inkremental ⇒ interval yang terlewat **tidak** ditagih kemudian (tanpa akrual ganda). Timer billing hanya di control plane (agent tanpa timer). §5.18 (ii), SPECS §7.12.
- **Tarif per server = overlay, bukan tier** (§5.18 (ii-b), SPECS §7.12): baris registry boleh membawa `rates.{cpu,ram,backup}` (hanya numerik > 0) yang meng-overlay tarif global `BILLING_RATE_*`; key kosong/cacat ⇒ global, plafon `BILLING_MAX_*` tetap global. Resolusi satu pintu `ServerRates` (cache per instance, tanpa secret), dihitung **saat tick** — tarif baru berlaku pada akrual berikutnya, `amount` invoice tetap dari akrual tersimpan. Alternatif "tarif per baris app/invoice dibekukan historis" ditolak karena menambah state yang harus dimigrasi tanpa manfaat penagihan.
- **Grant pemilihan server bukan ability app** (SPECS §6.1/§7.14, §5.26): `server_select`/`server_ids` di dokumen user hanya membuka pemilihan server (`ServerAccess::canSelectServer()`/`maySelect()`/`selectableServers()`) dan visibilitas/filter server (`visibleServers()`), **bukan** kelola registry (tetap admin-only, 404) dan bukan baris app/backup (tetap `AppAccess`/`BackupAccess`). Allowlist kosong = semua; allowlist yang seluruh id-nya invalid **ditolak**, jangan dinormalkan menjadi `[]`. Metrik host server tanpa app terlihat tidak pernah dikirim ke monitor.
- **Tanpa state lintas-request**: tidak ada property controller yang menyimpan data; semua state di session/file.
- **Tema tampilan disimpan di `localStorage`, bukan skema user** (§5.42, SPECS §7.17): preferensi `light|dark|system` murni klien — tanpa migrasi/kolom baru di SQLite/`auth.json`, tanpa route/controller/POST, dan sudah berlaku **sebelum** PHP merender halaman (anti-flash). Konsekuensi yang diterima: preferensi **per-browser/per-perangkat**, tidak ikut akun (tidak sinkron antar perangkat) dan hilang saat data situs dibersihkan.
- **Mount path sama dengan host (`${PWD}:${PWD}`)**: syarat agar relative bind mount milik app terselesaikan ke path host oleh daemon.
- **Disposisi sinyal adalah state proses, bukan state request**: `SIGCHLD=SIG_IGN` yang dipasang untuk auto-reap anak detached bocor ke proses anak berikutnya (diwariskan melewati `exec`) — di worker persistent ini merusak `git`/`docker compose`. Setiap spawn yang membaca exit code wajib memakai `SigchldGuard` (§4.4).
- **`container_name` bersifat global**: nama container custom tidak mendapat prefix project Docker (beda dari nama default compose), sehingga wajib divalidasi unik se-host **sebelum** menulis override — kalau tidak, `compose up` gagal di tengah deploy (`Conflict. The container name ... is already in use`, §5.12).
- **Override batas resource meniru keluarga field base compose**: Compose menolak mencampur key legacy (`cpus`/`mem_limit`) dengan `deploy.resources.limits.*` bernilai beda dan `!override` tidak menolong, jadi `ResourceLimits` memilih keluarga field **per service** mengikuti base — legacy untuk base tanpa blok `deploy.resources.limits` (portabel, terbukti tanpa warning deprecation), modern bila base sudah memakai blok itu, dan keduanya (nilai identik) bila base memakai keduanya (§5.12a).
- **Deteksi gaya limit diulang tiap `sync()`**: base compose app repo Git bisa berubah gaya setelah `git pull`/rollback, sehingga keluarga field tidak boleh di-cache dan `ResourceLimits` dijalankan ulang di setiap jalur `up` (§5.12a).
- **Multi-server: protokol agent = token + timestamp + nonce + signature (HMAC-SHA256) di kanal TLS ter-pin.** Canonical string `"{timestamp}\n{METHOD}\n{path}\n{sha256(body_hex)}"` identik di kedua sisi (`AgentClient::canonical()` ↔ `AgentAuthMiddleware`) — **jangan menyalin** ke tempat lain, satu penyimpangan byte memutus semua panggilan. Signature **opsional di sisi agent** (bila header tidak ada, baseline = token + timestamp + nonce + TLS), tetapi token **selalu wajib** — termasuk `/healthz` & `/version`.
- **Multi-server: TLS pinning dengan cert sebagai CA-nya sendiri.** PEM sertifikat agent disimpan di dokumen `servers` (self-signed = publik, bukan secret), dimaterialisasi ke `runtime/agent-tls/{id}.crt` per panggilan (`TlsPinMaterializer`) lalu dipakai sebagai `verify` Guzzle/curl — cURL memperlakukannya sebagai trust anchor. Ini dipilih daripada membandingkan `CURLINFO_CERTINFO` sendiri (rapuh). **Tidak ada** jalur `verify=false`; `base_url` wajib `https://`. Direktori baru `database/agent-certs/` **ditolak** sebagai lokasi (tidak tercakup `.gitignore` ⇒ berisiko cert ter-commit).
- **Multi-server: token agent tersimpan di kolom SQLite `servers` belum terenkripsi at-rest** (bisa ditambahkan bila diinginkan). Token tidak pernah dirender ulang (`publicServer()`/`formServer()` membuang/mengosongkannya) dan hanya masuk header — bukan body/URL — sehingga tidak muncul di log akses; `AgentError` menyaringnya dari pesan.
- **Multi-server: sertifikat agent berlaku 825 hari tanpa rotasi otomatis.** `install.sh --force` mengganti token + sertifikat ⇒ admin **wajib** memperbarui di halaman Servers; `AgentClient` mendeteksi kegagalan TLS (`AgentError('tls_failed')`) agar rotasi ketahuan tegas, bukan timeout misterius.
- **Multi-server: keunikan per server, bukan global.** Nama app/port/container/subdomain/project compose diperiksa terhadap app **di server itu** (dimensi dari `AppStore::serverIdOf()`); dua server boleh memakai nama/port/subdomain yang sama. Mengembalikan pemeriksaan ke global akan membuat server kedua mustahil dipakai (mis. `ports` yang sama di rentang berbeda tetap valid).
- **Multi-server: `server_id` default `local`, bukan kosong.** `AppStore::create()` menormalkan lewat `serverIdOf()`; dokumen lama di-`backfill` migrasi v2. Kosong/absen di mana pun = server lokal (jaring pengaman) — jangan menulis ulang `?: 'local'` di kelas lain (pakai helper).
- **Urutan `compose_files` & entri yatim punya satu penjaga**: urutan kanonik dimiliki **satu** kelas (`ComposeSource::orderFiles()` — base → reset → ports → names → limits → sisa generated pada urutan asli, env paling akhir; `AppController::orderComposeFiles()` hanya mendelegasi), dan sebelum `docker compose -f …` dijalankan, `LocalDeployer::resolveComposeFiles()` membuang entri override generated yang file-nya sudah tidak ada (`ComposeSource::filterMissingGenerated()`) — tanpa itu satu entri yatim membuat seluruh perintah compose gagal `no such file or directory` (§5.12a GOTCHA). Penjaga yang sama menuntut **pola hitung-ulang**: `LocalDeployer::syncManagedOverrides()` menyinkronkan semua override terkelola lalu memanggil ulang `resolveComposeFiles()`, sehingga berkas yang **baru ditulis** (mis. `docker-compose.override.env.yml` pada job `apply_env` server agent) ikut terkirim tanpa menunggu apply berikutnya (§5.12a GOTCHA, §5.37).
- **Proses tidak boleh me-recreate container yang menjalankannya** (§5.14): update dashboard dijalankan helper container terpisah; kalau dijalankan dari proses di dalam container target, container lama di-stop lebih dulu dan kegagalan di jendela itu meninggalkan dashboard mati.
- **GOTCHA — helper self-update tidak boleh di-attach ke network `internal: true`** (§5.14): dashboard **ikut** ter-attach ke network di luar compose — network helper Adminer `rames-helpers` (`internal: true`, permanen, `AdminerHelper::attachDashboard()`) dan network DB app saat dump/restore (`DbConnectionResolver::ensureSelfConnected()`). **Gejala**: update dari UI selalu gagal di tahap fetch — log helper `fatal: unable to access 'https://github.com/<repo>.git/': Could not resolve host: github.com` → `git fetch gagal` (rollback tidak terpicu karena repo belum berubah). **Sebab**: network `internal: true` tidak punya route keluar, jadi DNS eksternal gagal **walau `--dns 8.8.8.8` diberikan** (resolver `127.0.0.11` tak bisa meneruskan query). **Penangkal**: `UpdateService::chooseHelperNetwork()` memilih network **non-internal** milik project compose (`<project>_default`) dan **tidak** memakai network project lain sebagai pelarian (container dashboard hasil recreate tidak ada di sana → health-check gagal → rollback), **bukan** `array_key_first(NetworkSettings.Networks)` — urutan kunci JSON terurut abjad, dan `rames-helpers` < `rames_default`, sehingga network internal justru terpilih lebih dulu; bila tidak ada kandidat layak preflight menolak sebelum repo disentuh (kecuali Engine tidak menjawab sama sekali sehingga status `Internal` tak dapat dipastikan — di situ helper memakai preferensi lama `<project>_default` → network pertama, dan kegagalannya muncul di tahap `git fetch`, bukan sebagai penolakan awal). **Pemulihan instalasi yang sudah telanjur macet**: `docker network disconnect rames-helpers rames-webman` (atau satu kali `git pull` + `docker compose up -d --build --force-recreate webman` lewat SSH) → update berikutnya normal, karena helper baru sudah menjalankan kode terpilih ini.
- **`git ls-remote`, bukan `git fetch`, untuk cek pembaruan**: fetch menulis objek/ref ke `.git` sebagai root (dashboard = root, repo = milik user host) dan meninggalkan berkas milik root yang membuat `git pull` dari SSH gagal; selain itu repo "kotor" karena status berubah — padahal update justru butuh repo bersih.
- **restic di helper container, bukan di dashboard** (§5.15): dashboard tidak melihat filesystem named volume app, jadi backup/restore memakai `docker run --rm` yang nge-bind volume target (`:ro` untuk backup, `rw` untuk restore). Konsekuensinya binary restic harus ada di **image helper** (`Dockerfile`), kredensial diteruskan lewat `--env-file`/`--password-file` (file, bukan argv) agar tidak bocor ke `ps`, dan helper **tidak** mewarisi `dns:` compose sehingga `--dns` diambil dari inspect dashboard (`HelperImageResolver`) — sama seperti `UpdateService::selfContext()`.
- **Helper Nginx WAJIB berbagi network namespace host** (`--network host`, SPECS §8.4): helper `NginxReloader` me-chroot ke root host sehingga `nginx -t` membaca `/etc/resolv.conf` **host**, tetapi tanpa netns host `127.0.0.1` di dalam helper menunjuk loopback container — bila host memakai resolver lokal (`nameserver 127.0.0.1`, mis. systemd-resolved/dnsmasq), resolusi DNS gagal dan `nginx -t` menolak vhost `proxy_pass` hostname yang sebenarnya sah (`[emerg] host not found in upstream`) → false negative + rollback padahal config valid. **Konsekuensi**: resolusi & konektivitas uji identik dengan nginx host; risiko tambahan nihil karena helper sudah `--privileged` dan meng-mount `/:/host`.
- **Backup volume memakai namespace env terpisah dari backup DB**: `VOLUME_BACKUP_*`/`RESTIC_*`/`AWS_*` (§5.15) vs `DB_BACKUP_*` (§8i) — jangan digabung atau saling membajak nama.
- **Status backup dibaca dari cache, bukan live** (§5.15): `GET /api/backups/status` di-poll tiap `data-interval`, jadi menyentuh Engine + restic S3 tiap poll akan membuat halaman menggantung saat S3 lambat. Cache `BackupCatalog` ditulis akhir run & saat admin menekan **Segarkan** — satu-satunya jalur yang mengizinkan muat live.
- **Seleksi backup berkala disimpan di store terpisah** (store `backup`, koleksi `volumes`, `BackupSelection`, §5.15/§5.19), bukan di store `apps`: store `apps` tidak berubah, seleksi bersifat global per-**nama volume** (bukan per-app), dan default **OFF** (opt-in) — hanya volume yang **eksplisit** diaktifkan, atau di-`backfill()` karena sudah punya snapshot, yang ikut run harian; mencegah volume baru ikut terjadwal tanpa sengaja.
- **GOTCHA — kelas PHP tidak hot-reload di worker persistent**: perubahan `app/library/**`/controller kadang tidak berefek (mis. data baru tidak tampil) walaupun file di disk sudah benar. **Sebab**: worker Webman memuat kelas **sekali** saat boot; `controller_reuse=false` hanya soal state antar-request, **bukan** hot-reload kode. **Penangkal**: `docker exec rames-webman php start.php reload` setelah mengubah kelas yang dipakai runtime (view `app/view/**`/CSS tidak perlu — cukup hard refresh).
- **Rute proxy per app disimpan terstruktur, bukan snippet Nginx mentah** (§5.6a): bentuk `[{path, target}]` + validasi ketat `NginxRoutes` membuat dashboard tetap bisa memvalidasi & membatasi (maks 20 rute, path absolut, `/.well-known` dicadangkan untuk ACME, tolak `..`/userinfo/query) **sebelum** menulis config. Snippet mentah (`include`/`server`/`listen`/`server_name` dari user) sengaja tidak didukung — config rusak bukan sekadar app itu mati, karena `nginx -t` memvalidasi seluruh host (lihat §8, future work).
- **Penyimpanan rute wajib lewat `NginxConfigGuard` (uji + rollback)** (§5.6a): menulis config lalu mengandalkan watcher saja tidak aman karena watcher sengaja **tidak** reload saat `nginx -t` gagal (§8.3) — config rusak tetap tertinggal di disk dan memblokir reload berikutnya untuk **seluruh** host. Guard karena itu menyimpan secara transaksional: `nginx -t`/reload dulu, dan bila gagal `nginx_routes` + config lama dipulihkan. `applyRoutes()` **tidak melempar** — selalu mengembalikan `{ok, reloaded, rolled_back, error}`; karena rollback itu sendiri best-effort, `rolled_back` hanya berarti `apps.json` pulih (bukan jaminan file config di disk bersih), sehingga konsumen **wajib** menampilkan `error` (yang memuat `PERINGATAN` saat rollback gagal sebagian).

- **Subdomain disimpan sebagai label, bukan FQDN** (§5.6b, SPECS §7.11): `apps.json.subdomain` = label slug, FQDN efektif dirakit `app_subdomain_of()`. Dengan begitu subdomain bisa diubah tanpa mengganti `name` (yang dipakai sebagai nama project compose & direktori app); fallback ke `name` menjaga kompatibilitas app lama (tanpa migrasi), dan nilai lama ber-FQDN tetap dihormati. Penyimpanan memakai guard transaksional yang sama dengan rute (§5.6a/§5.6b) agar config Nginx invalid tidak pernah tertinggal (memblokir reload **seluruh** host); status SSL di-reset karena sertifikat terikat nama domain lama.
- **Shell terminal dipilih server (auto), bukan dipaksa klien** (§5.9): `DockerExec::resolveShell()` memprobe container (`bash`>`ash`>`sh`) sehingga Debian/dash & Alpine/BusyBox sama-sama dapat shell terbaik yang tersedia; `sh` = fail-safe (tanpa readline), dan dashboard **tidak** memasang binary tambahan ke container user.
- **File manager berjalan sebagai root (batas = ability `files`)** (§5.16): user image tidak berizin atas berkas milik user lain / bind mount root host, sehingga semua `docker exec` memakai `-u 0`; kompensasinya kepemilikan entri **baru** dipulihkan best-effort (`ownerSpec()`/`restoreOwner()`) dan operator+ adalah batas keamanan (viewer tidak boleh). `mv` lintas device & `docker cp` sengaja **tanpa** hook `chown`.
- **Transfer byte file manager lewat `docker cp` + berkas temp, bukan memori PHP** (§5.16): unggah/unduh/ekstrak memindahkan berkas di luar proses PHP (`memory_limit` 128 MiB tidak dinaikkan), dengan direktori temp `runtime/files-transfer/` yang dibersihkan `Workerman\Timer` (unduhan) + `prune()` (sisa yatim).
- **Ekstraksi arsip file manager dilakukan di host dashboard** (§5.16), bukan di container app: `unzip`/`tar` belum tentu tersedia di container app. Arsip divalidasi `ArchiveGuard` (tolak entri absolut/drive Windows/`..` **dan** symlink yang keluar dari direktori ekstraksi — zip-slip) sebelum/sesudah ekstraksi, lalu hasilnya disalin balik via `docker cp`.
- **Perintah file manager bebas shell** (§5.16): `docker exec` dibangun array + `sh -c` **di dalam container** dengan tiap argumen `escapeshellarg` (path/nama sudah dinormalisasi `PathGuard`), sedangkan perintah host (`docker cp`/`unzip`/`tar`) array + `bypass_shell` — tidak ada shell host yang merangkai string.
- **Container file manager wajib berjalan** (§5.16): operasi ditolak **409 fail-fast** (`assertRunning()`) bila container berhenti — dashboard tidak membuat container sementara maupun menyentuh volume Docker langsung; parser listing file manager sengaja portabel **BusyBox & GNU** (`stat -c`) agar Alpine & Debian sama-sama jalan.
- **Kredit top-up ditulis inline di dalam transaksi `TopUpOrder::settle()`** (§5.18), bukan memanggil `CreditAccount::deposit()`: `deposit()` membuka sendiri `SqliteStore::update()` (satu transaksi `BEGIN IMMEDIATE`), sehingga memanggilnya di dalam `settle()` yang sudah berada dalam transaksi akan menulis bersarang. `TopUpService::creditTopUp(&$data, …)` mereplikasi bentuk entri ledger `topup` milik `deposit(...,'topup',$reference)` (ditambah field `idr` = nominal rupiah nyata yang dibayar) tetapi langsung pada `&$data` transaksi yang sedang berjalan → transisi order + saldo + ledger atomik dalam **satu** transaksi.
- **Kurs top-up default 1:1 + provenance `idr` di ledger** (§5.18): `BILLING_TOPUP_IDR_PER_CREDIT` default **`1`** (Rp1 = 1 kredit) ⇒ angka `BILLING_RATE_CPU_PER_CORE_HOUR`/`BILLING_RATE_RAM_PER_GB_HOUR` = rupiah/jam. Kredit konversi **dibekukan di order** (`orders.<id>.credits`) sehingga mengubah kurs tidak mengubah order lama, dan entri ledger `topup` menyimpan `idr` (nominal nyata dibayar, dijaga `BillingStore::normalizeLedgerEntry`). View `/credits` **tidak menebak** padanan rupiah entri `topup` tanpa `idr` — menampilkan angka salah lebih buruk daripada tidak menampilkan.
- **Gerbang kredit: aktor exempt dikecualikan lebih dulu, lalu pembayar/owner** (§5.18): `AppController::billingAssertCanStart()` mengecualikan **aktor bebas tagihan (admin)** lebih dulu — admin **tidak pernah** diblokir kredit; lalu **app milik pihak bebas tagihan (admin) ⇒ diizinkan untuk siapa pun** (termasuk operator member tanpa saldo); baru sisanya dinilai: aktor `member` (wajib bersaldo) dan `owner/penanggung biaya` (`billingPayerFor()`: `owner_id`, fallback aktor) bila berbeda. Konsekuensinya admin bisa menyalakan app member bersaldo negatif; app itu **tetap** diakru & tetap dihentikan lagi oleh kebijakan `stop` (bukan jalur gratis). **Perubahan kebijakan ini menggantikan** aturan lama "admin yang mengoperasikan app milik member tetap bisa ditolak". Deteksi "bebas tagihan" memakai **role ter-resolve** (`BillingGate::roleIsExempt()`): admin legacy tanpa field `role` tetap bebas, store tak terbaca ⇒ tidak exempt (paling ketat). Worker `cli/deploy.php` kini **berparitas penuh**: `spawnWorker()` meneruskan id aktor (`argv[4]`), dan worker memakai urutan penilaian **aktor → pembayar/owner** dengan pengecualian exempt yang sama — aktor admin **atau** owner admin ⇒ dilewati; selain itu **aktor dinilai lebih dulu** (`$actor ?? $owner`) lalu **owner** bila berbeda dari aktor. Tanpa aktor (pemanggil lama/`argv[4]` kosong) worker menilai **hanya penanggung biaya/owner**. Ini menutup N2 lama (worker kini ikut menilai aktor pada kasus app tanpa owner/owner tak dikenal) sehingga putusan controller & worker konsisten. **Gerbang backup berkala mengikuti urutan yang sama** (`BackupController::assertCanScheduleBackup()` + helper `billingPayerFor()` lokalnya, hanya saat `scheduled=1`) — biaya akrual ditagihkan ke owner, jadi operator bersaldo cukup tidak boleh menyalakan fitur berbayar pada app milik member bersaldo kurang (pesan 402 menyebut pemilik app).
- **Signature Duitku = HMAC-SHA256** (§5.18): Duitku mengobsoletkan MD5/SHA-256 biasa (changelog Apr 2026); satu skema sah = `hash_hmac('sha256', …)` hex lowercase, diverifikasi `hash_equals`.
- **`billing_log_path` = seam pengujian** (§5.18): log meteran/auto-stop/callback/CLI menulis ke `runtime/logs/billing/` (default) atau direktori override — tes memakai path temp sehingga tidak pernah menyentuh log produksi.
- **Penagihan digerbang tanggal `BILLING_INVOICE_DAY` (dijepit 1–28)** (§5.18): `BillingRunner::invoiceDayReached()` mencegah penagihan periode berjalan terlalu dini bila batas bulan timezone dashboard berbeda dari timezone proses; catch-up tetap terjadi karena `runDue()` memilih periode **tertunggak** (`period < bulan berjalan`).
- **Pengalihan kepemilikan ke pemilik bebas tagihan = pemakaian gratis ⇒ dihentikan** (§5.18): `AppStopper::shouldStopOnTransfer()` (keputusan murni, teruji)
- **Multi-server: jalur data (backup/restore/dump) tidak pernah fallback ke server lokal** (§5.32): `BackupDispatcher` memutuskan **server** lebih dulu dan melempar bila server tak dikenal/disabled, volume yatim, atau app pemilik volume terdaftar di server lain — op data tidak boleh "kebetulan" berjalan di host control plane (plan §3 butir 4).
- **Multi-server: kredensial data milik server, bukan payload job** (§5.32/§10.5): payload job data hanya membawa penanda (`volume`/`snapshot`/`trigger`) + metadata app; env S3/restic/passphrase dibaca **di server itu** (`CredentialEnvFile` 0600). Karena itu agent bisa menjalankan backup tanpa pernah melihat kredensial control plane (dan sebaliknya).
- **Multi-server: registry/riwayat backup di-scope lewat kunci, bukan migrasi skema** (§5.32): `BackupRegistry::scopeKey()` = `<server_id>::<volume>` (server lokal tetap nama volume) sehingga dua server boleh punya volume bernama sama tanpa memecah/mengubah format store JSON lama. memisahkan aturan dari efek samping; `stopForBillingEscape()` (pengalihan manual) & `stopTransferredToExemptOwner()` (hapus user) memakai jalur stop yang sama dengan auto-stop saldo negatif (satu pintu `DeployerInterface::stop()`, tanpa Docker mentah), dengan **alasan `message` dibedakan** (`REASON` = saldo negatif, `REASON_TRANSFER` = pengalihan) via parameter `$reason` `stopOwnedBy()`.
- **Utang teknis (bukan bug) — normalisasi path SSL belum seragam & preflight bisa *false-negative*.** `deploy.letsencrypt_path`/`deploy.ssl_webroot` **belum** punya normalisasi setara `SslIssuer::dirSetting()` (yang baru dipakai `certbot_work_dir`/`certbot_logs_dir`): nilai berisi spasi saja masih bisa lolos ke argv certbot/`mkdir` — efeknya sebatas pesan certbot yang membingungkan, bukan jalur bypass otorisasi. `assertChallengePathServable()` juga bisa **meloloskan** yang sebenarnya gagal (`fileperms()` tak terbaca karena uid/gid tak diketahui, `open_basedir`, atau path tak terlihat di container); arahnya **aman** — certbot lalu melaporkan `403` + hint tindakan — jadi jangan diperlakukan sebagai celah keamanan.
