# 3. Mode Menjalankan (Environment)

> Bagian dari [dokumentasi arsitektur](../ARCHITECTURE.md) · Spesifikasi: [SPECS.md](../SPECS.md) · Panduan operasional: [DETAILS.md](../../DETAILS.md)

- Dashboard = container `rames-webman` (berjalan sebagai **root**), akses `http://host:{APP_PORT}`.
- Kode di-mount dengan path **sama dengan host** — `"${PWD}:${PWD}"` + `working_dir: ${PWD}`. Ini **krusial**: karena `docker compose` dieksekusi *di dalam container* tetapi daemon-nya *di host*, relative volume mount di `docker-compose.yml` milik app harus terselesaikan ke **path host yang valid**. Memakai `/app` membuat bind jadi `/app/apps/...` yang tidak dikenal daemon.
- `docker.sock` di-mount → dashboard mengeksekusi `docker compose` pada daemon host.
- Direktori Nginx host (`sites-available`/`sites-enabled`) di-mount → dashboard menulis file config; reload dilakukan watcher/manual di host.
- `/etc/letsencrypt` host di-mount → certbot (container) menulis sertifikat; nginx host membaca dari path yang sama.
- Named volume **`rames`** di-mount ke `/var/lib/rames` (di luar bind `${PWD}:${PWD}`) → menyimpan basis data SQLite `rames.sqlite` + snapshot backup-nya (§5.19); tidak hilang saat `git clean`/update dashboard. Berlabel `rames.role=dashboard-db` agar dikecualikan dari fitur backup volume app (§5.15).
- Container memakai `dns:` eksplisit (`DNS_1`/`DNS_2`) karena `/etc/resolv.conf` host pada environment ini bermasalah (symlink rusak) sehingga resolver internal Docker tak punya upstream.
- **Urutan bootstrap container (penting untuk provisioning).** `command:` compose menjalankan `composer install` (bila `vendor/autoload.php` belum ada — penanda berkas, bukan direktori `vendor/`, agar instalasi yang terputus tidak membuat bootstrap terlewat) → `php cli/db.php migrate` → `php cli/db.php import-json` → `php start.php start`, sedangkan container sudah berstatus `running` sejak detik pertama rantai itu. Karena itu "container running" **bukan** tanda dashboard siap. Satu-satunya jalur provisioning user admin adalah `host/create-admin.sh` (dipakai `host/install.sh`, bisa manual): ia memprobe `GET /healthz` dari **dalam** container (port internal `8787`, bukan `APP_PORT` host) sampai JSON `"ok":true` — tanda vendor terpasang + skema SQLite termigrasi + server listening — baru memanggil `php webman make:admin` (SPECS §6.3).
> **GOTCHA — "container `running`" ≠ "dashboard siap".** **Gejala**: `sudo ./host/install.sh` mencetak `PHP Warning: require_once(/…/vendor/autoload.php): Failed to open stream` + `PHP Fatal error: Failed opening required '…/vendor/autoload.php'` tepat setelah baris "Membuat user admin pertama", lalu dashboard tidak bisa dilogin; `docker exec rames-webman php webman make:admin` manual pun gagal sama. **Sebab**: `State.Running=true` sudah terpenuhi sejak detik pertama bootstrap `command:` compose, sedangkan `composer install` + `cli/db.php migrate` masih berjalan — `make:admin` menabrak `vendor/autoload.php`/skema DB yang belum siap. **Penangkal**: ukur kesiapan dari `GET /healthz` **dari dalam** container (`"ok":true`), bukan dari `.State.Running` — pola `host/create-admin.sh`; jalur manual wajib menunggu `docker compose logs webman` menunjukkan server listening.
- **Mode runtime `agent` (`RAMES_MODE=agent`)** — server #2..N memakai kode & image yang sama dengan mode dashboard, tetapi:
  - `config/route.php` hanya mendaftarkan route mesin (`GET /healthz`, `GET /version`, `POST /jobs`, `GET /jobs/{id}`, `GET /jobs/{id}/log`, `GET /apps/{id}`, `GET /apps/{id}/nginx`, `POST /nginx/check`, `POST /apps/check`) dan **hanya bila `AGENT_TOKEN` terisi** (fail-closed: tanpa token tidak ada route sama sekali → semua 404);
  - `config/middleware.php` memasang **`AgentAuthMiddleware` saja** (bukan CSRF/Auth sesi) — middleware bersifat global, jadi mode harus digerbangi di sini juga, bukan hanya di `route.php`;
  - `config/process.php` mengganti **hanya** tiga hal pada proses `webman`: `listen` → `http://{AGENT_BIND}` (default `0.0.0.0:8443`), `transport` → `ssl`, dan `context.ssl.local_cert`/`local_pk` (`verify_peer=false`). TLS diterminasi **di proses agent sendiri** (bukan Nginx host) supaya objek yang di-pin control plane adalah sertifikat agent;
  - **Fail-fast TLS**: `AGENT_TLS_CERT`/`AGENT_TLS_KEY` wajib ada & terbaca; tanpa itu startup dibatalkan (`RuntimeException`), tidak ada mode "tanpa TLS";
  - `agent/install.sh` menyiapkan `secrets/agent.env` (0600) + sertifikat self-signed (825 hari) + `docker-compose.agent.yml` (project `rames-agent`, container `rames-agent`) dan mencetak blok onboarding.
- **Timer**: mode agent tidak memasang timer dashboard (monitor/billing/backup DB/template pull); mode `dashboard` tidak tersentuh oleh perubahan mode.
- **Firewall**: dua kelompok port berbeda kebijakan — port agent (default `8443`) hanya boleh dibuka untuk IP control plane (allowlist lewat firewall server, bukan UI), sedangkan port web publik `80`/`443` **wajib terbuka untuk semua** (Nginx host + validasi HTTP-01 Let's Encrypt). Instruksi onboarding `agent/install.sh` mencetak keduanya — GOTCHA §8 no. 52.

> **GOTCHA — image dashboard wajib memuat plugin `buildx`.** **Gejala**: deploy app gagal dengan `Docker Compose requires buildx plugin to be installed` lalu `Building the --mount option requires BuildKit` (build `docker compose up --build` berhenti di `RUN --mount=…`). **Sebab**: image dashboard hanya memasang `docker-cli` + `docker-cli-compose`; tanpa plugin `docker-cli-buildx`, Compose **jatuh ke legacy builder** yang tidak mendukung `--mount`/cache mount. **Penangkal**: paket `docker-cli-buildx` dipasang di `Dockerfile`, dan paket docker (`docker-cli`/`docker-cli-compose`/`docker-cli-buildx`) diambil eksplisit dari repo `main`+`community` CDN resmi Alpine — mirror aliyun kadang sudah menyinkronkan indeks tanpa menyediakan berkas `.apk`-nya (`HTTP 404`), dan apk memakai entri repo pertama tanpa fallback. Container lama harus di-**recreate** setelah image dibangun ulang (memasang paket di container berjalan hanya bertahan sampai recreate); agent memakai image yang sama sehingga ikut terperbaiki.

> **GOTCHA — data runtime DILARANG masuk Docker build context.** **Gejala**: self-update dari dashboard gagal di tahap build dengan `checking context: no permission to read from '…/database/env/<app>.env'`, lalu helper rollback ke SHA lama — dashboard tetap versi lama. **Sebab**: tanpa `.dockerignore`, seluruh direktori repo dikirim sebagai build context; `database/env/*.env` (0600, pemilik root/uid lain), `database/keys/`, serta direktori runtime lain tidak terbaca oleh proses yang men-tar context, dan **legacy builder** (dipakai selama plugin `buildx` belum ada di image yang sedang berjalan) men-tar context secara eager sehingga build berhenti sebelum Dockerfile dieksekusi — bukan masalah Dockerfile. **Penangkal**: `.dockerignore` di root repo mengecualikan seluruh data runtime/secret (`database/`, `apps/`, `runtime/`, `nginx-status/`, `webroot/`, `secrets/`) plus `.git/`, `vendor/`, `tests/`; builder tidak menuruni direktori yang dikecualikan, jadi berkas tanpa izin pun aman, dan context mengecil (≈2 MB) sehingga update lebih cepat. **WAJIB**: Dockerfile sengaja **tanpa `COPY`/`ADD`** (kode dibaca dari bind mount `${PWD}:${PWD}`) — jangan menambah `COPY` yang menunjuk direktori yang dikecualikan tanpa menyesuaikan `.dockerignore`.

> **GOTCHA — buildx/BuildKit menolak `network.host` tanpa entitlement.** **Gejala**: deploy/rebuild app gagal setelah image dashboard memakai BuildKit: `additional privileges requested: pass "--allow=network.host" to grant requested privileges` (atau `failed to solve: … network.host is not allowed`) untuk app yang compose-nya memakai `build.network: host` atau Dockerfile-nya `RUN --network=host` — padahal app yang sama dulu berhasil. **Sebab**: legacy builder mengizinkan jaringan host saat build, BuildKit tidak. BuildKit mensyaratkan **dua** hal: definisi build **meminta** entitlement (`build.entitlements`) **dan** klien **memberikannya** (`--allow`). Compose v5 selalu membangun lewat buildx bake, menulis `build.entitlements` ke definisi bake, tetapi **tidak** meneruskan `--allow` — sementara buildx 0.38+ menolak request yang meminta entitlement tanpa grant (buildx 0.37 masih lolos, sehingga regresi ini tidak terlihat di host dengan buildx lama). **Penangkal** (dua bagian, keduanya wajib): (1) `BuildEntitlements::sync()` dipanggil `LocalDeployer::upCompose()` sebelum build, menulis `docker-compose.override.build.yml` (`build.entitlements: [network.host]` untuk service ber-`build:`) dan menyisipkannya ke daftar `-f` **sebelum** override env — file transien, tidak masuk `compose_files`; (2) `DockerComposeRunner::up($build=true)` **tidak** memakai `up --build` lagi, melainkan mengambil definisi build milik Compose (`docker compose build --print`) lalu menjalankannya dengan `docker buildx bake -f <definisi> --allow network.host`, baru `docker compose up -d` setelah image siap. Definisi bake diambil dari Compose supaya context/build args/tag identik — **jangan** menyusun ulang konfigurasi build sendiri. Detail alur: SPECS §7.6c.
