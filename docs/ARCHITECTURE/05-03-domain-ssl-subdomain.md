# 5. Alur Utama — Domain, SSL & Subdomain

> Bagian dari [dokumentasi arsitektur](../ARCHITECTURE.md) · Spesifikasi: [SPECS.md](../SPECS.md) · Panduan operasional: [DETAILS.md](../../DETAILS.md)

## 5.6 Custom Domain & SSL per Domain

1. Halaman detail app → form **Set Custom Domain** (FQDN publik valid, unik di semua app, bukan subdomain sendiri). App **tanpa host port** ditolak lebih dulu dengan pesan jelas (tidak ada target `proxy_pass`) — subdomain & SSL-nya memang tidak berlaku (§5.1).
2. Set → update `apps.json` (`custom_domain` + `custom_ssl_status=disabled`) → tulis ulang config Nginx: subdomain menjadi block redirect `301` ke `http(s)://{custom_domain}`, custom domain melayani app (`LocalDeployer::renderNginxConfig`); **setiap domain tambahan** (`apps.json.custom_domains[]`) menjadi serve block sendiri, tanpa redirect — rincian di *Domain tambahan (alias)* di bawah. Status SSL **per slot**: blok redirect subdomain memakai `ssl_status` (slot `ssl`) — bila `active`, generator merender 80→https + blok 443 dengan cert subdomain; target redirect tetap `https` **hanya** bila `custom_ssl_status=active` (cert subdomain tidak mengubah target).

   **Target DNS wajib disebut (langkah UI setelah simpan/saat belum aktif).** `DomainSettingsController::setDomain()` menambahkan flash `<A|AAAA> record <domain> ke <alamat> (server <label>)`, dan `InfoController::detail()` mengirim `serverAddress` ke `app/view/app/partials/detail-tab-domain.php` (alert info + teks bantuan). Sumber tunggal: `ServerAddress::forApp()` (`app/library/Deploy/ServerAddress.php`) — field registry `address` → `public_ip` → `ip`, lalu host `ServerResolver::baseUrl()` server **pemilik app**, **tanpa resolusi DNS** (aturan keras: host-lookup memblokir worker Webman persistent ±4 s dan fallback A record subdomain app sudah dihapus); hanya alamat **publik** (IP privat/loopback/reserved & `.local`/`.internal`/`.lan` ditolak; hostname publik dipakai apa adanya), `''` bila tak pasti ⇒ kalimat generik `A/AAAA` "ke IP server tempat app ini berjalan" + tautan `/servers`. Jenis record dari `ServerAddress::recordType()`; alert **tidak dirender** bila `custom_ssl_status=active` (SSL sudah aktif). Hanya ability `domain` yang melihat alamat — `detail()` mengirim `''` untuk viewer; token/PEM/`base_url` utuh tidak pernah tampil (GOTCHA no. 25). Label server: lokal selalu `lokal`, agent `name` → fallback `id` (sama antara flash dan kartu; field alamat server belum diekspos di UI `/servers`). Sebab: domain diarahkan ke IP server lain ⇒ HTTP-01 `404` walau vhost & webroot benar (GOTCHA no. 28). Pengujian: `tests/ServerAddressTest.php`, `tests/AppControllerServerAddressFlashTest.php`.
3. Ganti/hapus custom domain → `SslIssuer::revoke()` mencabut sertifikat lama (no-op bila belum ada cert), lalu config ditulis ulang (subdomain kembali melayani app).
4. SSL custom domain → tombol di detail app & `/domains` (tab **Semua Domain**: **satu baris per domain** — domain utama, tiap domain tambahan berlabel `(domain tambahan)`, lalu subdomain redirect) → permintaan **masuk antrean global** (`ssl_jobs`; satu job dieksekusi pada satu waktu, §5.44) → `SslQueueWorker` menjalankan `cli/ssl.php <appId> <domain>`; worker menentukan slot lewat `AppDomains::slotOf()` (`ssl` subdomain, `custom_ssl` domain utama, `alias:<domain>` domain tambahan), **menulis ulang vhost + reload Nginx lebih dulu** (`SslChallengeVhost::ensure()`, reload gagal = fatal, §5.27 — blok acme harus dimuat dari webroot sekarang), menjalankan certbot (preflight izin + preflight visibilitas webroot di host), lalu tulis ulang config Nginx (443). Subdomain redirect dapat di-SSL-kan **terpisah** dari custom domain — status tetap per slot. Baris `pending` menampilkan posisi antrean (SPECS §8a).

> **Domain tambahan (alias) — `apps.json.custom_domains[]`, maks 20.** `custom_domain` tetap **domain utama** (subdomain tetap 301 ke sana); `custom_domains[]` = daftar **domain tambahan** `{domain, ssl_status, ssl_stage, ssl_message, ssl_error, ssl_expires_at, created_at}`. Setiap alias **melayani app langsung** — serve block ke host port primary yang sama, **tanpa** redirect — sehingga app merutekan tenant/site sendiri dari header `Host`. Alias boleh ada tanpa domain utama (subdomain lalu tetap serve). Satu pintu domain ↔ slot & status per slot: `app/library/Domain/AppDomains.php` — slot `ssl` (subdomain), `custom_ssl` (domain utama), `alias:<domain>` (domain tambahan), batas `MAX_ALIASES = 20`. **WAJIB** membaca/menulis status lewat `AppDomains::status()`/`writeStatus()`; jangan membaca `$app[$slot.'_status']` sendiri untuk slot alias (statusnya tinggal di entri `custom_domains[]`).
>
> - **Render vhost** — `LocalDeployer::domainServerBlocks()` merender berurutan: subdomain (serve bila tanpa domain utama, selain itu redirect `301`), domain utama (serve, bila ada), lalu **satu serve block per alias**; blok `listen 443 ssl` alias hanya bila `AppDomains::status($app, 'alias:<domain>')['ssl_status'] === 'active'` (cert `live/<alias>/`). Alias yang kebetulan sama dengan subdomain/domain utama (data rusak hasil sunting manual) **dilewati** agar `server_name` tidak dobel. Blok ACME (`/.well-known/acme-challenge/`) dirender di **setiap** server block. Vhost agent memakai library yang sama: `custom_domains` ikut diproyeksikan (`AgentAppProjection` metadata + `AgentJobController::APP_FIELDS`), jadi tidak ada render khusus agent.
> - **Tambah alias** — `POST /apps/{id}/domains` (field `domain`) → `DomainSettingsController::addDomain`: ability `domain` (`findApp(..., 'domain')` ⇒ tanpa hak **404**) → app wajib punya host port (`AppPorts::hasHostPort`) → `AppDomains::assertAliasAddable()` (FQDN publik, bukan subdomain/domain utama app ini, tidak duplikat, batas 20) → keunikan **per server** lewat `AppDomains::ownerOf()` terhadap subdomain efektif + `custom_domain` + alias app lain, plus bentrok domain parkir (`ParkedDomainStore::byDomain()`) — semua **sebelum** efek samping → simpan entri `ssl_status=disabled` → tulis config Nginx → reload (best-effort) → flash **hint DNS A/AAAA** (`domainDnsHint()`, sumber `ServerAddress::forApp()`; SPECS §8b). Gagal tulis config ⇒ domain tetap tersimpan + pesan "jalankan Rebuild".
> - **Hapus alias** — `POST /apps/{id}/domains/remove` (field `domain`): hanya entri yang cocok dibuang → revoke sertifikat **best-effort di server pemilik app** (`AppSslRevoker`; app agent ⇒ job `ssl_revoke`; gagal revoke = peringatan `info`, domain **tetap** dihapus) → tulis config + reload.
> - **Aktivasi SSL** — `POST /ssl/{id}/enable` (& `/api/ssl/{id}/enable`) kini menerima **domain apa pun milik app** lewat `AppDomains::slotOf()` (`null` ⇒ "bukan milik app ini"); antrean global `ssl_jobs` dedupe key `app:{id}:{domain}:{slot}`; slot alias dipertahankan hanya bila domainnya masih terdaftar, selain itu jatuh kembali ke `ssl` (`SslQueue::normalizeAppSlot()`).
> - **Tabel `/domains` & polling** — `SslDomainRows::appRows()` menghasilkan satu baris per domain: domain utama (`is_custom`, `serve`), tiap alias (`is_alias`, `serve`, label `(domain tambahan)`), lalu subdomain (`redirect` bila ada domain utama, `serve` bila tidak). Kunci baris/polling `data-domain-key` = **`kind:id:role:domain`** (bukan `kind:id:role`) karena domain utama & alias sama-sama `role=serve` — tanpa `domain` dua baris akan saling menimpa saat polling; cache-buster `ssl.js?v=6`.
> - **Data rusak** — `AppDomains::aliases()` membuang entri bukan-array/`domain` bukan string/domain tak valid/duplikat, memotong ke `MAX_ALIASES`, dan menormalkan field status non-skalar (`ssl_status` ⇒ `disabled`, field lain ⇒ `null`; hindari warning "Array to string conversion"). Pemanggil tidak perlu bercabang untuk data lama.

> **GOTCHA — domain utama = alias app sendiri ⇒ slot alias tak bisa di-SSL-kan & baris kembar.** **Gejala**: bila data memuat domain yang sama sebagai domain utama **dan** alias (mis. hasil sunting manual), `/domains` menampilkan dua baris domain identik dan status baris alias tidak pernah berubah walau sertifikat domain itu terbit — penerbitan selalu tercatat di slot `custom_ssl`. **Sebab**: `AppDomains::slotOf()` memprioritaskan `custom_ssl` di atas `alias:<domain>`, sehingga domain itu selalu dipetakan ke slot domain utama; `LocalDeployer::domainServerBlocks()` juga melewati alias kembar. **Penangkal**: `DomainSettingsController::setDomain()` **menolak** domain yang sudah menjadi alias app itu sendiri (pesan "hapus dulu dari daftar domain tambahan") dan `assertAliasAddable()` menolak alias = subdomain/domain utama — jangan melonggarkan kedua cek itu.
>
> **WAJIB — `writeStatus()` tidak menghidupkan alias yang sudah dihapus.** **Gejala**: domain yang baru dihapus muncul lagi di config Nginx/`/domains` sesudah worker SSL selesai. **Sebab**: job `alias:<domain>` bisa tuntas **setelah** entri `custom_domains[]` dihapus; menulis status "buta" (membuat entri baru) akan menghidupkan kembali domain itu. **Penangkal**: `AppDomains::writeStatus()` memetakan slot lewat `domainOfSlot()` dan **no-op** bila alias tidak lagi terdaftar — semua penulis status (controller, `cli/ssl.php`, `cli/deploy.php` untuk revoke, `SslQueueWorker`) wajib lewat kelas ini.
>
> **GOTCHA (batasan diketahui) — status alias app agent tidak ikut ditarik dari agent.** **Gejala**: di control plane, alias app di server agent bertahan `pending`/tanpa pesan walau cert sudah terbit di agent; `ssl_message`/`ssl_stage`/`ssl_error` alias tidak terisi. **Sebab**: setelah job SSL di agent, `cli/ssl.php` menarik state agent (`AgentDeployer::appState()`) tetapi hanya memakai **`ssl_expires_at`** — field pesan/stage/error alias tidak ada di daftar tarik (sama seperti `custom_ssl_message/stage/error` yang sudah ada). **Penangkal**: status terminal `active`/`failed` tetap konvergen karena ditulis control plane sendiri; untuk diagnosis baca log job di server itu (`runtime/logs/deploy/{appId}.log`), jangan mengandalkan pesan galat agent pada alias.

## 5.6a Rute proxy tambahan per app (Simpan & Terapkan + rollback)

> Terkait: SPECS §8.2a. Field `apps.json` `nginx_routes`; blok `location ^~ <path>` di-render `NginxConfigGenerator::render()` **hanya** di serve block (HTTP 80 & HTTPS 443).
>
> **Semantik blok (mount subpath, §8.2a):** prefix `path` **dilepas** ke upstream (`proxy_pass {target}/`), URL balik upstream (Location relatif maupun absolut ke origin target) di-`proxy_redirect` ke prefix, prefix dikirim sebagai `X-Forwarded-Prefix`, `proxy_http_version 1.1` + `Upgrade $http_upgrade` + `Connection "upgrade"` (literal, tanpa `map`), dan timeout proxy 60 s. Sebelumnya `proxy_pass` meneruskan path penuh tanpa `X-Forwarded-Prefix`, sehingga aset absolut upstream (yang mengasumsikan dirinya di `/`) menunjuk ke app utama — bukan ke rute.
>
> **Tanpa `map` WebSocket.** Blok rute memakai `Connection "upgrade"` literal (sama dengan `location /` app). **GOTCHA — jangan render `map $http_upgrade` dari berkas config app**: `map` mendaftarkan variabel baru di konteks `http`; pada host dengan config padat `nginx -t` gagal dengan `could not build variables_hash, you should increase variables_hash_bucket_size` (gejala: simpan rute di-rollback, error `emerg` di flash, reload seluruh host terblokir). Penangkal: literal `"upgrade"`; bila butuh `$connection_upgrade`, definisikan sekali di `nginx.conf` host, bukan per app.

1. Detail app → kartu **Rute Proxy Tambahan** (ability `routes` = operator ke atas; `AppControllerBase::findApp($id, 'routes')` → tanpa hak = **404**). App tanpa host port (`AppPorts::hasHostPort`, §5.1) ditolak lebih dulu dengan pesan prasyarat — **sebelum** efek samping apa pun.
2. `POST /apps/{id}/routes` → `DomainSettingsController::saveRoutes`: textarea (`<path> <target>` per baris; baris `#` = komentar; kosong = `[]` = hapus semua) di-parse `NginxRoutes::parse()` (fail-fast). Kesalahan **per baris** (format maupun isi) menyebut **nomor baris textarea** (`Baris N: …`); kesalahan **lintas-entri** (duplikat `path`, batas `MAX`) berasal dari `normalize()` akhir tanpa nomor baris tetapi menyebut nilai path-nya.
3. `NginxConfigGuard::applyRoutes($id, $routes)` menjalankan transaksi "uji dulu":
   - snapshot `nginx_routes` lama (mentah);
   - `AppStore::update()` menyimpan rute baru;
   - `DeployerInterface::writeNginxConfig()` menulis ulang config app — rute dirender lewat `NginxRoutes::all()` di `LocalDeployer::renderNginxConfig()`;
   - `NginxReloader::reload()` (`nginx -t` + reload host, §5.6/§8.4).
4. **Bila gagal** (tulis config melempar, atau uji/reload menolak) → guard **rollback**: pulihkan `nginx_routes` ke nilai lama + tulis ulang config lama; host **tidak** di-reload. `applyRoutes()` **tidak pernah melempar** — selalu mengembalikan 4 kunci `{ok, reloaded, rolled_back, error}`:
   - `rolled_back=true` = rute lama berhasil dipulihkan di `apps.json`;
   - `rolled_back=false` + `error` memuat `PERINGATAN: rollback gagal: …` = pemulihan `apps.json` gagal → rute baru tetap tersimpan;
   - `rolled_back=true` + `error` memuat `PERINGATAN: config lama gagal ditulis ulang: … (periksa/Deploy Ulang)` = `apps.json` pulih tetapi config di disk bisa tetap versi baru.
   Controller menerjemahkan hasil menjadi flash + `redirect('/apps/{id}')`; konsumen **wajib** menampilkan `error`, bukan hanya membaca `rolled_back`. **Alasan**: `nginx -t` memvalidasi seluruh config host; config invalid yang tertinggal di disk memblokir reload nginx **seluruh host** (semua app + renewal SSL) karena watcher sengaja tidak reload saat validasi gagal (§8.3) — rollback wajib.
5. Regenerate lain (deploy/rebuild/rollback/SSL) juga memanggil `NginxRoutes::all()` di `renderNginxConfig()`, sehingga rute ikut ditulis ulang otomatis tanpa langkah tambahan.

**Jebakan (ringkas; rinci di SPECS §8.2a)**: G1 `target` hostname wajib resolvable dari host Nginx; G2 `/.well-known` dicadangkan (jangan timpa blok ACME); G3 `setDomain`/`removeDomain`/`cli/ssl.php` (& deploy) **belum** lewat guard (rute hanya ter-render, tanpa rollback transaksional); G4 rollback best-effort — `rolled_back=true` **tidak** menjamin file config di disk bersih, dan kegagalan rollback `apps.json` (`rolled_back=false`) meninggalkan rute baru tersimpan; G5 tanpa lock per-app (dua simpan bersamaan bisa *lost update*); G7 `all()` best-effort vs `normalize()`/`parse()` fail-fast; G8 non-atomik terhadap crash (proses mati antara persist & reload → jalankan ulang/Deploy Ulang).

**Pengujian**: `tests/NginxRoutesTest.php`, `tests/NginxConfigGuardTest.php`, `tests/NginxConfigGeneratorTest.php`.

## 5.6b Ubah Subdomain app (label terpisah dari nama)

> Terkait: SPECS §7.11, §8.1. Field `apps.json.subdomain` menyimpan **label** slug (mis. `blog-x7k2`), bukan FQDN. FQDN efektif dirakit `app_subdomain_of($app)` = `{label}.{APP_DOMAIN}`, fallback `{name}.{APP_DOMAIN}` bila field kosong; nilai lama berupa FQDN penuh (mengandung titik) dihormati apa adanya (tanpa migrasi data).

1. Tab **Domain & SSL** di detail app (ability `domain` = operator+; `AppControllerBase::findApp($id, 'domain')` → tanpa hak = **404**) menyediakan input label subdomain + tombol simpan (AJAX ke `POST /apps/{id}/subdomain`; fallback form biasa = flash + redirect). App tanpa host port (`AppPorts::hasHostPort`, §5.1) ditolak lebih dulu dengan pesan prasyarat.
2. `DomainSettingsController::setSubdomain` (controller mediator) membuat `SubdomainManager` + `NginxConfigGuard` lalu memanggil `SubdomainManager::change($appId, $label)`:
   - **validasi** format label (`app_subdomain_valid()`: `[a-z0-9-]`, awal/akhir alfanumerik, maks 63) + keunikan atas **FQDN efektif** semua app lain (termasuk app yang memakai fallback `name`) + bentrok `custom_domain` (`assertAvailable()`);
   - **idempoten**: FQDN efektif sama dengan lama → `noop`, tanpa efek samping;
   - `NginxConfigGuard::applySubdomain($appId, $label|null)`: snapshot `SUBDOMAIN_STATE_KEYS` → `AppStore::update()` menyimpan label + **reset status SSL** → `DeployerInterface::writeNginxConfig()` → `NginxReloader::reload()` (`nginx -t` + reload host).
3. **Bila gagal** → `rollbackState()` memulihkan `SUBDOMAIN_STATE_KEYS` ke nilai lama **dan** menulis ulang config lama (best-effort); reload **tidak** dipanggil bila config tidak sempat ditulis. `applySubdomain()` **tidak melempar** — selalu mengembalikan `{ok, reloaded, rolled_back, error}`.
4. **Respons**: JSON sukses `{code:0,noop,subdomain,previous,reloaded,message}`; gagal `{code:1,error,subdomain}`. Permintaan non-JSON → `flash_set` + `redirect('/apps/{id}')`.
5. **Reset SSL wajib**: sertifikat Let's Encrypt terikat nama domain lama → `ssl_status=disabled`, `ssl_stage`/`ssl_message`/`ssl_error`/`ssl_expires_at` = `null`, `needs_ssl=false`. Reset hanya slot **`ssl`**; `custom_ssl_*` tidak diubah (status per slot). Berkas sertifikat **tidak** dihapus/dipindah; user menerbitkan ulang lewat tab Semua Domain (subdomain redirect akan mendapat 443 setelah cert subdomain aktif).
6. **Alur create** (git §5.1 / compose §5.1b / template §5.1c) menerima field `subdomain` opsional: divalidasi format + keunikan (`assertSubdomainAvailable()`) **sebelum menyentuh disk**, disimpan di session `pending_app['subdomain']` hanya bila tidak kosong, lalu diteruskan `createAndDeploy()`. Halaman konfirmasi menampilkan FQDN efektif **read-only** (view tidak merender field `subdomain`); form create mem-prefill `{nama}-{6 alfanumerik acak}` dengan *dirty flag* + `pattern`/`maxlength=63` yang identik `app_subdomain_valid()`.

> **GOTCHA — sertifikat SSL lama tidak valid setelah subdomain berubah.** Gejala: app yang tadinya HTTPS kini gagal verifikasi/`ERR_CERT_COMMON_NAME_INVALID` setelah subdomain diganti. Sebab: sertifikat Let's Encrypt terikat pada **nama domain** (`{domain}/live/…`), bukan pada app; mengganti subdomain membuat cert lama tidak cocok. Penangkal: status SSL di-reset otomatis saat subdomain berubah — **terbitkan ulang** sertifikat lewat tab **Semua Domain** (`/domains`) atau kartu SSL di tab **Domain & SSL** detail app (berkas cert lama sengaja **tidak** dihapus agar rollback/domain lama tetap bisa dipakai).

**Pengujian**: `tests/SubdomainTest.php` (helper `app_subdomain_of`/`_label`/`_is_custom`/`_valid` + `SubdomainManager::assertAvailable()`/`change()`), `tests/NginxConfigGuardTest.php` (rollback `applySubdomain`).
