# 4.4 Background Worker — `cli/deploy.php`

> Bagian dari [dokumentasi arsitektur](../ARCHITECTURE.md) · Spesifikasi: [SPECS.md](../SPECS.md) · Panduan operasional: [DETAILS.md](../../DETAILS.md)

- Dipanggil detached oleh `AppController` via **`pcntl_fork` + `pcntl_exec`** (bukan `proc_open`). Alasan: `proc_close()` memblokir request sampai worker selesai — build bisa berlangsung menit, sehingga timeout/refresh browser tampak "menggagalkan" deploy. Request langsung kembali (hanya fork), worker berjalan detached (`posix_setsid`, stdio → `/dev/null`) dan tetap lanjut meski HTTP worker di-restart. Logging tetap oleh worker sendiri (`file_put_contents`).
- **Jebakan `SIGCHLD` (`SigchldGuard`)** — worker deploy & sesi terminal tidak pernah di-`wait`, jadi proses HTTP worker meng-ignore SIGCHLD (`SIG_IGN`) agar tidak ada zombie. Tetapi `SIG_IGN` **diwariskan melewati `fork` + `exec` dan menetap selama worker hidup** — semua proses yang di-spawn worker itu setelahnya ikut meng-ignore SIGCHLD. Akibatnya: (a) proses yang menunggu anaknya sendiri gagal `waitpid()` (ECHILD) — git → `git-remote-https`/index-pack, `script` → `docker exec`, `docker compose` → docker → `error: waitpid for git-remote-https failed: No child process` / `error: waitpid for --shallow-file failed: No child process` / `fatal: index-pack failed`; dan (b) `proc_close()` tidak bisa membaca exit code (selalu `-1`) sehingga perintah yang sukses dianggap gagal.
  Penangkalnya `app\library\Support\SigchldGuard`: `disableIgnore()`/`withDefault()` memasang `SIG_DFL` **sebelum** spawn (disposisi diwariskan saat `fork`, jadi harus berlaku sampai proses di-wait/`proc_close`) lalu `ignoreAndReap()` memulihkan pola auto-reap + membuang zombie sisa. Dipakai `ProcessRunner` (seluruh perintah git/docker), `DockerExec::open()` (sesi terminal), dan `DbDump::runToFile()`. Di sisi worker anak, `SIGCHLD` di-reset ke `SIG_DFL` sebelum `pcntl_exec` agar `ProcessRunner` di dalam worker membaca exit code dengan benar.
- UI deploy/rebuild memakai **AJAX + polling**: `fetch` pada tombol (tanpa navigasi halaman) + polling `/api/apps/{id}/status` menampilkan progres live (progress bar + stage + pesan). Bila halaman di-refresh saat build berjalan, page mendeteksi status `deploying` (panel `data-busy`) lalu melanjutkan polling otomatis sampai `running`/`error`.
- **Log deploy on-demand (popup modal)**: tombol `⧉ Log build` di panel progres, tombol `⧉ Lihat log deploy` pada alert error, dan tombol `⧉ Log deploy` di tab Deployment membuka `#deploy-log-modal` (partial `detail-modal-deploy-log.php`) — isi hanya dimuat saat modal dibuka. Modal membaca `GET /api/apps/{id}/deploy-log?tail=1` lalu polling `?offset=N` (header `X-Rames-Offset`), menampilkan tahap worker **dan output build `docker compose` live**. **Output build dialirkan**: `DockerComposeRunner::up(..., $onOutput)` → `ProcessRunner::runStreaming()` → `LocalDeployer::upCompose()` menulis baris utuh lewat `$logger('output', …)`; worker menulis stage `output` **mentah ke log tanpa `AppStore->update()`** (satu baris build bukan perubahan status; menulis ulang JSON per baris akan membanjiri store). Polling berhenti saat modal ditutup / `pagehide`.
- **Batalkan build** (`POST /apps/{id}/deploy/cancel`, ability `deploy`): worker deploy adalah pemimpin sesi (`posix_setsid`), sehingga `DeployCanceller` mengirim sinyal ke **grup proses** (`-pid`) — `docker compose`/build ikut berhenti. PID dicatat saat spawn (`launch(..., &$pid)` → `apps.worker_pid`); bila tidak ada, worker dicari via `/proc` dengan pencocokan `cli/deploy.php` + id app (aman dari PID reuse). Untuk app agent, `AgentDeployer::cancelJob()` dipanggil lebih dulu lalu worker control plane dimatikan; status app dipulihkan (`running` bila container lama hidup, selain itu `stopped`).
- Mode: `deploy`, `rebuild`, `rollback` (dengan argumen ref SHA), `apply` (app mode compose — `up -d` tanpa build, §5.1b), `stop`/`start`/`teardown`/`apply_env`/`apply_limits` (§5.12a — sinkron override limits + `up -d` tanpa build; di server agent dijalankan dari metadata `limits`), op F2 `nginx_write|nginx_remove|nginx_reload|ssl_issue|ssl_revoke` (§5.27 — cabang mode di `cli/deploy.php` **sebelum** gerbang kredit; menjalankan library Nginx/SSL **di server tempat worker berjalan**), op data F4 `backup_run|restore|db_dump` (§5.32), dan **op tingkat server** F4 lanjutan `template_pull|self_update|restore_archived` (§5.34 — tidak terikat app: `argv[1]` berisi *target* (slug template / `agent` / nama volume arsip) dan bloknya berjalan **sebelum** pemuatan app di store). Daftar mode di berkas ini adalah **satu-satunya** sumbernya: `DeployWorkerLauncher::MODES` mengikutinya, dan `AgentJobController::OPS` = `capabilities` (`GET /version`) merujuk konstanta itu — jangan menyalin daftarnya. Pipeline per tahap menulis status ke `apps.json` (via `AppStore->update`, `flock`), sehingga UI bisa *poll*:
  `deploying` → `build` → `collect` → `nginx` → `running` (atau `error`).
- Setelah selesai, persisten `containers` dan `deploy_history` kembali ke `apps.json`.
- Log per app: `runtime/logs/deploy/{appId}.log`.
- Worker SSL: `cli/ssl.php` — jalankan `certbot certonly`, update `ssl_status`/`ssl_expires_at`, tulis ulang config Nginx dengan SSL (log `runtime/logs/ssl/{appId}.log`). **Tidak lagi di-spawn controller**: `SslController`/`ParkedSslEnabler` hanya menulis job `ssl_jobs`, lalu proses timer `ssl-queue` (`app/process/SslQueueProcess` → `SslQueueWorker`) menjalankannya **sinkron** lewat `ProcessRunner` — satu job pada satu waktu (§5.44).
- Worker SSL **domain parkir**: `cli/parked-ssl.php {id}` — dijalankan `SslQueueWorker` dari job `ssl_jobs` (dulu detached oleh `ParkedSslEnabler`, kini enqueue saja); memanggil `ParkedSslIssuer::issue()` (validasi → certbot/reconcile → state `active`/`failed` → tulis config `_parked_*.conf` + reload), log `runtime/logs/ssl/parked-{id}.log` (SPECS §8j.6a).
- **Penjadwal antrean SSL (§5.44)** — proses timer `app/process/SslQueueProcess` (registrasi `config/process.php` blok `!$ramesIsAgent`, `count=1`, `reloadable=true`): `Timer::add(FIRST_DELAY=10, …, false)` lalu `Timer::add(5, …)` memanggil `SslQueueWorker::tick()`; penjaga `$busy` hanya re-entrancy di dalam proses (bukan state lintas-request). Semua `Throwable` ditangkap & dicatat ke `runtime/logs/ssl/queue.log` agar proses persistent tidak mati. Mode `agent` tidak menjalankan antrean (tidak punya store otoritatif/worker certbot lokal). **Proses baru ⇒ butuh restart (bukan `reload`) saat pertama di-deploy** (GOTCHA §5.44).
- **Self-update dashboard** (§5.14) — bukan worker PHP, melainkan **helper container** yang di-spawn `UpdateService` (`docker run -d`, detached, di luar compose project) dan menjalankan `cli/self-update.sh` di dalam repo: gate kepemilikan (`[ -w ]` pada `$ROOT`, `.git`, `.git/objects`, `.git/refs` — daftar sama dengan `helperWritablePaths()`, **sebelum** git apa pun; berlaku update **dan** rollback) → `git fetch`/`merge --ff-only` → `composer install` (bila perlu) → `docker compose up -d --build --force-recreate` → tunggu `/healthz` → rollback otomatis (`git reset --hard` + rebuild) bila versi baru tidak sehat. Seluruh git lewat `run_git()` (jejak `stdout`+`stderr` ditangkap & ditulis ke log sekaligus dipakai mengklasifikasi galat): jejak berpola izin/kepemilikan (`insufficient permission`, `Permission denied`, `unable to create/open/write`, `dubious ownership`, `safe.directory`, …) ⇒ pesan UI **kepemilikan/izin** + perintah `chown`, sedangkan pesan jaringan/DNS lama hanya dipakai bila jejak bukan pola izin. Status ditulis oleh `cli/update-report.php` (PHP mandiri tanpa autoload, ikut disalin ke `/tmp` agar stabil saat kode berubah oleh `git pull`).
- **Worker billing (§5.18)** — dua jalur memakai `BillingRunner`: **proses timer** `app/process/BillingProcess.php` (registrasi `config/process.php`, pola `UpdateCheckProcess`: `Timer::add(FIRST_DELAY=30, …, false)` lalu `Timer::add(BILLING_SAMPLE_SECONDS, …)`; `BILLING_ENABLED=false`/`BILLING_SAMPLE_SECONDS=0` ⇒ tanpa timer; semua `Throwable` ditangkap & dicatat ke `runtime/logs/billing/` agar worker persistent tidak mati) dan **CLI** `cli/billing.php` (`status|sample|tick|invoice [--period=YYYY-MM]|expire`) untuk operasi manual/verifikasi (mis. via `docker exec` bila dashboard sempat mati). Wiring callable top-up (expire/reconcile) **lazy** — hanya bila `BILLING_TOPUP_ENABLED` + merchant code + API key terisi, sehingga gateway tidak pernah disentuh saat fitur mati.
- **Worker deploy `cli/deploy.php` cek gerbang kredit sadar-aktor** (§5.18, pertahanan berlapis): `AppController::spawnWorker()` meneruskan **id aktor** sebagai `argv[4]` (`currentActorId()`; `ref` `argv[3]` selalu diisi — string kosong bila bukan rollback — agar posisi argumen stabil), lalu worker menjalankan **paritas penuh** dengan controller: **aktor admin ⇒ bebas**, **app milik admin ⇒ bebas untuk siapa pun**, selain itu dinilai berurutan **aktor → pembayar/owner** (`BillingGate::assertCanStart()`; `actor`/`owner` di-resolve `findPublicById`, owner tak diketahui ⇒ jatuh ke aktor). Gagal ⇒ app ditandai `status=error` + pesan `BILLING: …`, exit non-zero (tanpa efek samping). Bila aktor **tidak** dikirim (pemanggil lama/`argv[4]` kosong) perilaku lama dipertahankan: worker menilai **hanya penanggung biaya/owner** (jangan mengunci app). Id aktor tampak di **`argv` proses worker** (bukan rahasia — jalur audit `ps`/log `runtime/logs/deploy/{appId}.log`).
- **Worker backup DB (§5.19)** — proses timer `app/process/DbBackupProcess.php` (registrasi `config/process.php`, `count=1`): `Timer::add(FIRST_DELAY=45, …, false)` lalu `Timer::add(300, …)`; tiap tick memeriksa `DbBackup::isDue()` (fitur aktif + jam `DB_BACKUP_HOUR` terlewati + belum ada run/snapshot hari ini) → `run('scheduled')`. `DB_BACKUP_ENABLED=false` ⇒ tanpa timer; semua `Throwable` ditangkap & dicatat ke `runtime/logs/db-backup/` agar worker persistent tidak mati. Proses **baru** ⇒ butuh **restart** (bukan `reload`) saat pertama kali di-deploy. Selain timer, `cli/db.php` menyediakan operasi manual/verifikasi (`status|migrate|import-json|export-json|integrity|backup|list|prune|restore`).

- **Worker deploy di server agent (job async, multi-server F1)** — `DeployWorkerLauncher` memakai mekanisme spawn yang sama (`pcntl_fork`+`pcntl_exec`, `SigchldGuard`) tetapi di **server agent** `AgentJobController` yang memanggilnya. Env `RAMES_JOB_ID` (dan `RAMES_JOB_DIR` opsional, seam uji) membuat worker menandai rekaman `AgentJobStore` (`pending → running → done|error`) — **best-effort**: kegagalan menulis rekaman job tidak menggagalkan deploy. Tanpa env itu (jalur control plane/manual) `AgentJobStore` **tidak pernah** disentuh. Daftar mode worker (`DeployWorkerLauncher::MODES`) adalah satu sumber dengan validasi `POST /jobs` (capabilities agent).
- **Worker agent baru butuh restart**, bukan hanya reload, saat pertama diaktifkan (proses/route/middleware agent berbeda — pola yang sama dengan `db-backup`).
