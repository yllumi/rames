# 4.5 Storage

> Bagian dari [dokumentasi arsitektur](../ARCHITECTURE.md) · Spesifikasi: [SPECS.md](../SPECS.md) · Panduan operasional: [DETAILS.md](../../DETAILS.md)

> Konvensi: sebutan `apps.json`/`auth.json`/`billing.json`/`backup.json` di bagian lain dokumen ini merujuk pada store SQLite terkait (§5.19) — kecuali eksplisit menyebut berkas **warisan** yang diimpor sekali.

- **Basis data SQLite (`rames.sqlite`)** — semua data domain (§5.19): `config('deploy.sqlite_file')` (default `<RAMES_DB_DIR>/rames.sqlite`; di produksi = isi named volume `rames` → `/var/lib/rames`). Satu berkas memuat store `apps`, `auth`, `billing`, `backup`, `servers`, `parked`, `branding`; tabel `{store}_{koleksi}`; dokumen JSON di kolom `data` (**sumber kebenaran**) + kolom turunan terindeks + `ord`. Berkas DB + sidecar WAL/SHM di-gitignore (`database/*.sqlite*`) — tidak pernah ter-commit.
- **WARNING — DB di dalam direktori repo = salah deploy** (§5.19): memperbarui kode tanpa **recreate** kontainer (`docker compose up -d`, atau tombol **Update** yang menjalankan `compose up --build --force-recreate`) membuat env `RAMES_DB_DIR` + mount volume tidak berlaku → DB jatuh ke default `base_path()/database/rames.sqlite` (**di dalam repo**). Saat kontainer di-recreate kemudian, volume `rames` masih kosong → impor ulang JSON lama, dan perubahan yang terjadi di DB "di dalam repo" itu **hilang**. Penangkal: selalu recreate (jangan hanya `restart`/`reload`); `php cli/db.php status` mencetak `WARNING` bila `file` berada di dalam `base_path()`.
- store `apps` (tabel `apps_apps`) — dokumen app (struktur lengkap di SPECS §7.1): id, name, **source** (`git` default bila absen | `compose`), **template** (`{slug,title}` untuk app hasil template §5.1c, null untuk lain), **owner_id**, **members** (map userId → {role, added_at, added_by}, SPECS §7.7), subdomain, repo_url, branch, local_path, primary_service, **container_prefix** (prefix nama container, SPECS §7.6a), status, compose_files, auth_method, ssh_key, containers, timestamp, env (map KEY=value, SPECS §7.6), **limits** (map service → `{cpus, memory_mb}`, SPECS §7.6b), **server_id** (id server pemilik app di registry; kosong/absen = `local` — normalisasi satu jalur `AppStore::serverIdOf()`/`normalizeServerId()`, §5.25/§5.26). Kolom turunan terindeks: `name`, `owner_id`, `status`, `source`, `subdomain`, `server_id`.
- store `servers` (tabel `servers_servers` — invarian `{store}_{tabel}`, bukan `apps_servers`) — **registry server** multi-server (§5.26, SPECS §7.14): dokumen `{id, name, kind (local|agent), enabled, domain, notes, base_url, token, tls_cert_pem, tls_fingerprint, port_range{start,end}, status, agent_version, capabilities, last_seen_at}`; kolom turunan `name`, `kind`, `enabled`. Baris `local` di-seed migrasi skema v2 (`seedLocalServer()`) dan `server_id` app lama di-`backfill` ke `local` (`backfillAppServerId()`), tulis ke dokumen JSON **dan** kolom (JSON = sumber kebenaran). Migrasi v2 memakai `ensureDerivedColumns()` — **ALTER dulu, indeks kemudian** (GOTCHA §8).
- store `auth` (tabel `auth_users`) — dokumen user (id, username, password_hash, **role** `admin|member`, created_at, email). Dokumen lama tanpa `role` dibaca sebagai user pertama = admin (dokumen tidak ditulis ulang). Kolom turunan terindeks: `username`, `role`, `email`.
- store `parked` (tabel `parked_domains`) — **domain parking** (§5.38, SPECS §8j): entitas **global, tidak terikat app**. Dokumen `{id, domain, mode, redirect_to, redirect_code, server_id, created_by, created_at, updated_at}`; `id` = `pd_` + 12 hex; `mode` = `html|redirect`; kolom turunan `domain`, `server_id`, `mode`. Dibuat migrasi skema **v3** (`ensure()` idempoten) sehingga DB v1/v2 ikut mendapat tabelnya.
- store `branding` (tabel `branding_settings`) — identitas brand dashboard (§5.40, SPECS §7.16): satu dokumen `id=branding` `{name, logo, updated_at}`; `logo` = **nama berkas** saja (`logo.png|logo.jpg|logo.webp`), bukan path. Default `Rames`/`logo=null`. Dibuat idempoten `ensure()` (tanpa versi migrasi baru; `LATEST` tetap 3). **Berkas logo tidak di sini** — lihat butir berikut.
- `{RAMES_DB_DIR}/branding/logo.<ext>` — **berkas** logo brand kustom (ditulis `BrandingLogo`; di produksi `/var/lib/rames/branding`, ikut named volume `rames`). Nama berkas **tetap** (nama unggahan tidak dipakai), tulis atomik `.tmp` → `rename`. **BUKAN** bagian snapshot DB (§8i.4): snapshot hanya menyalin SQLite, jadi menghapus volume/berkas = logo hilang dan dashboard kembali ke `/logo-small.png`. Fallback dev `database/branding/` (gitignored).
- `database/parked/{id}/index.html` — **konten** halaman parkir mode `html` (gitignored), ditulis `ParkedDomainContent`. **BUKAN** bagian SQLite: snapshot DB (§5.19) hanya membawa metadata, jadi direktori ini wajib ikut backup host/berkas (GOTCHA §8 no. 43).
- `database/{apps,auth,billing,backup}.json` — berkas JSON **warisan** (tidak dihapus): diimpor **sekali** ke SQLite saat koneksi pertama (`DB_IMPORT_LEGACY_JSON`, flag `kv.legacy_imported_at`, §5.19); bisa diekspor balik via `php cli/db.php export-json`.
- `templates/<slug>/` — definisi template create app (§5.1c): `template.yml` (metadata + deklarasi env), `docker-compose.yml` (image prebuilt), `guide.md` (panduan Markdown opsional, dibaca `TemplateCatalog::readGuide()` — katalog-only, **tidak** di-materialize), `files/` (file pendukung). Ikut versi repo (bukan data runtime) → dikelola admin/dev lewat git.
- `host/restic-setup.md` — panduan setup backup volume ke S3 (Markdown **repo**, bukan data runtime) yang dirender **di dalam UI** pada `GET /backups/guide` (admin-only, §5.15): dibaca `BackupController::guideHtml()` → `Markdown::toHtml()` (satu pintu sanitasi), tampil sebagai kotak `.guide-content`; ikut versi repo lewat git, **tidak** disalin ke app.
- `database/keys/` — pasangan kunci SSH (deploy key per app, chmod 0600) + `known_hosts`; private key tidak pernah keluar server.
- `database/env/{name}.env` — managed env file per app (chmod 0600); dibaca docker compose via `--env-file`.
- `apps/{name}/docker-compose.override.limits.yml` — override **batas CPU/memori** generated (`ResourceLimits`, SPECS §7.6b/§5.12a); ditulis/dihapus mengikuti field `limits` di store `apps`.
- `apps/{name}/docker-compose.override.build.yml` — override **entitlement BuildKit** generated (`BuildEntitlements`, SPECS §7.6c): `build.entitlements: [network.host]` untuk tiap service ber-`build:`. **Transien** — ditulis tepat sebelum `docker compose up --build` dan **tidak** masuk `compose_files`; dihapus sendiri bila tidak ada service yang butuh.
- `runtime/update/check.json` — cache hasil cek pembaruan dashboard (§5.14), ditulis proses `update-check`/tombol **Cek Pembaruan**; dibaca badge nav tiap render halaman (tanpa jaringan).
- `runtime/logs/update/` — `run.json` (status update terakhir/sedang berjalan) + `<id>.log` (keluaran mentah git/composer/compose/curl), ditulis helper self-update.
- `runtime/backup/` — state backup volume (§5.15, gitignored): `status.json` (run terakhir, dibaca UI), `runs/*.json` (riwayat, retensi), `run.lock` (`flock`), `staging/` (dump logis sementara), `restore/` (kerja restore), `tmp/` (env-file kredensial per-run 0600), `catalog.json` (cache baris ringkasan — dibaca `GET /api/backups/status`, ditulis saat run/Segarkan).
- `runtime/db-backup/state.json` — status run/prune/restore terakhir backup DB SQLite (§5.19, ditulis `DbBackup` via `JsonStore`).
- `runtime/files-transfer/` — berkas temp transfer **file manager container** (§5.16, gitignored): staging unduh/unggah/ekstraksi lewat `docker cp`; tiap operasi memakai subdirektori acak, dibersihkan `Workerman\Timer` (unduhan, setelah respons di-stream) + `prune()` (sisa yatim > 1 jam).
- `runtime/logs/files/{date}.log` — audit operasi file manager (JSON per baris: `ts`, `user`, `app`, `app_id`, `container`, `action`).
- store `backup` (tabel `backup_volumes` + `backup_registry`) — **dua koleksi** (§5.15, §5.19) — dahulu satu berkas `database/backup.json` berisi dua kunci: koleksi `volumes` = seleksi backup **berkala per volume** (`BackupSelection`) dan `registry` = riwayat permanen volume yang **pernah ter-backup** (`BackupRegistry`, agar volume yang sudah dihapus tetap bisa dipulihkan). Bentuk entri: `volumes` `{"<nama>":{"scheduled":bool,"updated_at":ISO,"updated_by":id}}`; `registry` `{"<nama>":{"project":str,"app_id":?str,"app_name":?str,"strategy":str,"first_backed_up_at":ISO,"last_backed_up_at":ISO,"last_snapshot":?str,"snapshots":int,"bytes":int}}`. Untuk `volumes`, entri/kunci `scheduled` absen ⇒ default **OFF** (opt-in): volume tidak ikut run harian sampai entri eksplisit ditulis. Pengecualian: volume **ber-snapshot > 0** di-`backfill()` otomatis ke `scheduled=true` (`updated_by="system"`) saat `refreshCatalog()`/akhir run; entri eksplisit tidak ditimpa. Untuk `registry`, tiap volume `ok` dicatat akhir run; entri dipangkas saat snapshot habis — **kecuali** peta counts kosong (`[]`)/`null` yang dianggap "tidak diketahui" (GOTCHA §5.15). **Catatan**: `POST /backups/refresh` **menulis** koleksi ini (via `backfill()` + `syncRegistryCounts()`), bukan hanya `runtime/backup/catalog.json`.
- store `billing` (tabel `billing_users`/`billing_usage`/`billing_orders`) — **kredit/billing** (§5.18, §5.19) — dahulu `database/billing.json`: `users` (saldo + ledger per user), `usage` (akumulasi meteran per app + snapshot `name`/`owner_id` + field aditif `backup_gb`/`backup_credits_pending`), `orders` (order top-up Duitku). Semua mutasi lewat satu transaksi `SqliteStore::update()` (`BillingStore`); bentuk kanonik `{version,users,usage,orders}` dipertahankan.
- `database/restic/password` — passphrase restic (chmod 0600, gitignored), dirujuk `RESTIC_PASSWORD_FILE` (§5.15).
- `runtime/agent-jobs/{id}.json` + `{id}.log` — **registry job agent** (§5.23, gitignored): status/stage/pesan per job + log worker; `payload` disimpan **setelah redaksi** nilai ber-kunci sensitif. Di control plane direktori ini tidak dipakai.
- `runtime/agent-nonces.json` — cache anti-replay nonce `AgentAuthMiddleware` (nilai **ter-hash** sha256, TTL 120 s, `JsonStore` + `flock`); hanya ada di server agent.
- `runtime/agent-tls/{serverId}.crt` — PEM sertifikat agent hasil materialisasi `TlsPinMaterializer` dari dokumen `servers` (dipakai sebagai `verify`/trust anchor pemanggilan agent); hanya ada di control plane.
- `secrets/agent.env` (0600, `/secrets/` di-gitignore) + `secrets/agent/tls.{crt,key}` — identitas & rahasia **server agent** (`AGENT_TOKEN`, `AGENT_TLS_CERT/KEY`, `AGENT_BIND`, `APP_DOMAIN`, `PORT_RANGE_*`, `RAMES_MODE`), ditambah kunci SSL server itu (`ADMIN_EMAIL`, `SSL_CHALLENGE`, `SSL_CA_SERVER`, `CLOUDFLARE_CREDS`, opsional `CERTBOT_WORK_DIR`/`CERTBOT_LOGS_DIR` di wilayah operator — lihat §5.27), dibuat `agent/install.sh`; diinjeksi via `env_file` (jangan pernah lewat blok `environment:` — Compose menang atas `env_file`). Berkas ini ber-**sentinel**: blok `# rames-installer:begin` … `# rames-installer:end` = kunci terkelola (ditimpa tiap rerun), sedangkan baris setelah `# rames-installer:preserved` = **wilayah operator** yang disalin verbatim dan **aman** terhadap rerun (mis. `SSL_WEBROOT`, `LETSENCRYPT_PATH`, kunci kustom) — jangan menaruh penyetelan manual di dalam blok kelolaan (`agent/README.md` §"Rahasia & sumber konfigurasi").
- Data domain ditulis lewat `SqliteStore::update()` (satu transaksi `BEGIN IMMEDIATE`) → atomik tanpa penulisan parsial; **cache runtime JSON** lewat `JsonStore::update()` dengan `flock` → aman dari race condition.
- Direktori `apps/`, `database/*.json`, `database/*.sqlite*`, `database/keys/`, `database/env/`, `nginx-status/` di-gitignore (data runtime).
